# Слепой контрольный прогон закрытого эпика

Цель — проверить, насколько Codex воспроизводит поведение и инженерные решения по исходной постановке при меньшем участии пользователя. Совпадение строк изменений не является критерием.

Предпочитай контрольный эпик, который не использовался при создании навыков и примеров. Если пользователь явно выбрал знакомый эпик, не предлагай заменить его и не останавливай прогон. Пометь результат как диагностический, укажи известное загрязнение контекстом и не используй совпадение формата `delivery-writing` как доказательство независимого воспроизведения.

## Разделение данных

Используй двухфазный прогон и свежих вспомогательных агентов с `fork_turns: "none"`:

1. Куратор читает закрытый эпик, журнал изменений, связанные PR и историю Git. Он определяет момент отсечения до первой реализации и исторический `base_sha` для каждого репозитория.
2. Куратор возвращает исполнителю только очищенный пакет состояния на момент отсечения: заголовок, описание и критерии, существовавшие тогда дочерние задачи, допустимые связанные документы, репозитории и `base_sha`. Он не возвращает итоговые статусы, поздние комментарии, рекомендации к тестированию, PR, коммиты, изменения кода и детали исторического решения.
3. Исполнитель работает только по очищенному пакету. До `seal_campaign_candidate` он не открывает исходный закрытый эпик, метаданные разработки и исторические ветки или PR.
4. После фиксации кандидата свежий оценщик читает исторический результат и сравнивает его с кандидатом.

Если пользователь не указал `cutoff_at`, куратор выбирает последний момент до первой реализации по журналу изменений Jira и времени первого связанного коммита или PR. Зафиксируй этот выбор и безопасный `base_sha`, но не раскрывай решение исполнителю. Если восстановить честный срез нельзя, останови прогон как `needs_human`, а не называй его слепым.

## Исполнение

Первой задачей кампании добавь предварительную проверку фактически нужных runtime, package manager, registry, контейнеров и доступности Claude. Проверяй доступ к ресурсу, а не наличие VPN или другой конкретной сетевой схемы. Операционный сбой отмечай `blocked` или `interrupted`; `needs_human` используй только когда действительно требуется действие пользователя.

Создай рабочее дерево от исторического `base_sha` каждого репозитория в режиме detached HEAD. Каждая последовательная задача завершается чистым атомарным локальным коммитом до финальных проверок и ревью; следующая использует `base_from_task`, поэтому её v1 run видит только собственный diff. После единственной корректировки измени тот же коммит и повтори проверки. Независимые задачи с непересекающимися областями можно выполнять параллельно в отдельных рабочих деревьях от одного `base_sha`, только если это последний блок реализации репозитория. Для двух и более задач одного репозитория всегда добавь зависимую задачу с `role: integration`: её run использует исходный `base_sha`, проверяет объединённый diff, проектные команды и получает отдельное независимое ревью. Для параллельного блока сначала влей исходные коммиты через `git merge --no-ff` и проверь `git merge-base --is-ancestor <sha> HEAD` для каждого SHA. Не меняй текущие рабочие ветки и ничего не отправляй в удалённый репозиторий.

В чистом координирующем рабочем дереве вызови `create_campaign` с режимом `replay`, `cutoff_at` и очищенными задачами. Для каждой `implementation`-задачи передай точный корень исторического рабочего дерева, базу или `base_from_task`, а в её `create_run` — ссылку на кампанию. Запускай отдельного исполнителя на каждую готовую задачу через `spawn_agent` с `fork_turns: "none"`, одновременно не более трёх; его пакет должен содержать только очищенный срез. Выполняй задачу через v1 `workflow`; проверки должны соответствовать исторической версии репозитория, но их нельзя ослаблять из-за возраста кода. Интеграционного исполнителя запускай так же без унаследованного контекста. Записывай только реальные вмешательства пользователя с видом `context`, `blocking_question`, `correction`, `approval` или `external_unblock`. Запросы статуса и операционные переходы задач не записывай как вмешательства.

После первого подтверждённого лимита Anthropic сервер открывает общий предохранитель кампании. Пока интервал не истёк, следующие критики не вызывают Claude и явно используют `codex_fallback`; после истечения один следующий модельный этап становится пробой. Успешная проба возвращает Claude в работу, новый лимит продлевает интервал. Не проси пользователя вручную сообщать о сбросе лимита.

Когда все задачи завершены, до дополнительных правок вызови `seal_campaign_candidate`. Он проверит, что текущие изменённые пути покрыты завершёнными прогонами v1, и сохранит Git-снимок каждого рабочего дерева. Для параллельного репозитория оценщик сравнивает с историей итог интеграционного рабочего дерева, а снимки отдельных задач использует только для проверки происхождения изменений. Только после успешной фиксации разрешено читать исторические PR, коммиты, итоговые комментарии Jira и изменения кода.

## Сравнение

Оценщика запускай через `spawn_agent` с `fork_turns: "none"` только после фиксации кандидата. Он выставляет по каждой шкале целое значение от 0 до 4:

- `scope` — покрыт ли тот же пользовательский и системный объём;
- `behavior` — совпадают ли наблюдаемое поведение, API и граничные случаи;
- `architecture` — сопоставимы ли границы модулей, зависимости и эксплуатационные решения;
- `tests` — проверены ли те же риски и регрессии;
- `operability` — сопоставимы ли диагностика, конфигурация, безопасность и выпуск.

`0` означает отсутствие результата или противоречие, `2` — частичное совпадение с существенными разрывами, `4` — эквивалентный результат без значимых расхождений. Оценщик выставляет `cutoff_rubric` за соответствие очищенному контракту и `rubric` за сходство с исторической реализацией. Для каждого существенного расхождения он указывает причину `derivable_miss`, `underspecified`, `historical_only` или `intentional_alternative`, отдельно выбирает готовность `unsafe | partial | ready`, а затем записывает всё через `record_campaign_comparison`; сырой diff в состояние не попадает.

Итоговый отчёт отдельно показывает соответствие исходному контракту, историческое сходство, готовность кандидата, существенные отличия и реальные вмешательства пользователя. Операционные переходы задач покажи отдельно. `finish_campaign(status: complete)` означает `campaign_status: evaluated`, а не готовность кандидата. Не публикуй результаты и не изменяй закрытый эпик без отдельной команды.
