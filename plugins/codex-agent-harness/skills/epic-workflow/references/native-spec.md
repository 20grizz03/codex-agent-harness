# Нативные спецификации Agent Harness

Для новой кампании по умолчанию используй локальные Markdown-черновики в `.agent-harness/specs/<change-id>/`. В `spec.md` держи общий для эпика продуктовый и технический контракт; в `tasks/<task-id>.md` — контракт ровно одной задачи кампании. Идентификаторы файлов задач должны совпадать с переданными в `create_campaign` идентификаторами, включая исследовательские, интеграционные и служебные задачи; не используй имена, отличающиеся только регистром. Для самостоятельного `create_run` достаточно `spec.md`, без эпика и каталога `tasks/`.

До разбиения на задачи исследуй реальные репозитории, компоненты, внешние контракты и ограничения среды. Общая спека фиксирует архитектурные границы, изменяемое поведение, инварианты, ошибки и восстановление, безопасность данных, совместимость, порядок внедрения и проверяемые результаты. Спека задачи уточняет её собственное поведение и технический объём, сценарии проверки, зависимости и границу PR. Ориентир 300–700 изменённых строк рабочего кода остаётся мягким: тесты и другие файлы учитывай отдельно, неделимое превышение объясни. Не добавляй обязательные заголовки, YAML, слова `MUST`/`WHEN`/`THEN` или проверку OpenSpec CLI ради нативного формата. [Пример общей спеки](../assets/native-spec/epic.md) и [пример задачи](../assets/native-spec/task.md) показывают возможное содержание, а не схему.

Сопоставь требования с задачами и каждую задачу — с проверяемым сценарием. Закрепи версии нужных внешних и межкомпонентных контрактов в `contract_refs` и проверь, что их можно прочесть. Вопрос, меняющий продукт, область или границы задач, оставь для `analysis` и укажи `readiness: analysis_required`: такая кампания содержит только исследовательские задачи, без приблизительной реализации. Готовый пакет получает `readiness: ready`. Обычные технические решения внутри согласованных границ принимает ведущий.

Перед созданием черновиков добавь `/.agent-harness/specs/` в локальный `.git/info/exclude`, если правило ещё не действует, и проверь `git check-ignore` для пути. Покажи пользователю общую спеку и все спеки задач одним пакетом. Утверждение этого пакета один раз разрешает согласованные обратимые локальные действия; внешние записи по-прежнему требуют отдельного разрешения.

Документы должны быть непустыми UTF-8-файлами без NUL и симлинков, не больше 256 КиБ каждый и 2 МиБ суммарно. Не помещай в них ключи, токены, пароли, приватные ключи или URL с учётными данными. Проверка также может отклонить безобидный пример присваивания значения полям `token`, `password` или заголовку `Authorization`; описывай такие поля и источник секрета словами, без значения. При отказе сервер называет файл, но не выводит его содержимое. Уже утверждённый снимок проверяется по хешам и правилам безопасного чтения, без повторного применения правил приёмки текста.

Создай кампанию с `spec: {kind: "harness", change_id: "<change-id>", readiness: "ready"}` (или `analysis_required`). Для самостоятельного прогона передай такой же необязательный `spec` в `create_run`, когда нужен закреплённый контракт. Сервер проверяет полный набор файлов и сохраняет их закрытый снимок с режимом `0600` в Git-метаданных. Получай абсолютные пути снимка через `get_campaign` или `get_run` в `spec_context`; не подставляй рабочие черновики вместо снимка. Исполнителю связанного прогона передай только общую спеку и его собственную спеку задачи. Спеки зависимостей добавляй лишь точными ссылками в контракте задачи, когда без них нельзя выполнить её границу; несвязанные задачи по умолчанию не загружай.

После создания черновики можно редактировать без остановки кампании, но эти изменения не меняют утверждённый снимок и не расширяют разрешение. Существенная перемена плана или поведения требует нового согласованного ограниченного контракта и новой кампании либо прогона; прежний снимок не переписывай. Нативный формат не вводит автоматическую классификацию изменений или перенос ревизий. Для уже созданной кампании сохраняй её `spec.kind`; не преобразуй действующий OpenSpec-контракт автоматически.
