# Обычный путь эпика

## Исходные данные и готовность

Прочитай эпик Jira, дочерние задачи, связи, актуальные комментарии и открытые вопросы. Для каждого репозитория проверь `AGENTS.md`, `CLAUDE.md`, Git, активные PR и проверки. Используй Jira и GitHub Enterprise MCP для метаданных, локальный Git по SSH — для кода и истории. Не переноси случайные детали старой реализации в продуктовый контракт.

Для сложной работы подготовь обязательный [OpenSpec](openspec.md). До задач реализации проверь:

- известны компоненты и репозитории, а также их владельцы;
- каждому требованию соответствует хотя бы одна задача, а каждой задаче — проверяемый сценарий;
- изменяемые контракты приложены или разрешаются по ссылке, имеют закреплённую версию и доступны исполнителю;
- описаны существенные состояния, ошибки, повторы и восстановление;
- определены совместимость, миграции, порядок локального внедрения, публикация и откат.

Для применимых механизмов до реализации разбери холодный старт и пустой результат, конкурентные чтение/обновление, заполненный кеш или очередь, одинаковую версию с изменённой свежестью, частичный/некорректный пакет, тайм-аут и отмену, верхнюю границу времени и ресурсов. Для каждого существенного сценария укажи ожидаемое поведение и проверку. Не добавляй кеш, очередь или новые требования только ради этого списка; неизвестный продуктовый смысл уточняй, технические границы выбирай внутри контракта.

Укажи `Статус: ready`, когда оставшиеся технические решения можно принять внутри этих границ. Вопрос, меняющий продукт, область, контракт или состав задач, получает `Статус: analysis_required` и отдельную исследовательскую задачу вида `analysis`; не создавай приблизительные задачи реализации.

## Задачи и контракт кампании

Задача вида `implementation` содержит одну функциональность и даёт одно законченное наблюдаемое поведение. Задача вида `analysis` закрывает вопрос без изменения репозитория. Задача вида `delivery` собирает данные кандидата, но не пишет финальный текст и не публикует.

Ориентир реализации — 300–700 строк рабочего кода. Тесты, документацию, конфигурацию, сгенерированные и бинарные файлы оценивай отдельно. Для связного превышения запиши `exception_reason`. Превышение мягкого бюджета не блокирует проверки или ревью.

Перед показом плана выполни самопроверку и, если задача смешивает независимо выпускаемое поведение, переразбей её до показа пользователю. Например, задачу с несколькими независимо выпускаемыми операциями разумно делить по этим операциям, а неделимое обновление версии PHP оставлять одним срезом, если промежуточное состояние не собирается.

Вызови `create_campaign` с `mode: delivery` и ссылкой `source {kind, ref}` на фактический источник. Для каждой подготовленной задачи сохрани:

- точные `goal` и `done_when`, ограничения, нецели и обязательные проверки;
- `contract_refs` вида `{ref, revision}`; OpenSpec добавляется как закреплённая ссылка автоматически;
- `review_budget`, `max_correction_passes` и `max_critic_retries`;
- `execution.native_model`, `execution.reasoning_effort` и `execution.escalation_model`;
- `wave`, локальные `dependencies`, `base_sha` или `base_from_task` и `dependency_strategy`;
- рабочее дерево, ожидаемые пути, Jira, PR, сообщение коммита и способ проверки.

Для новых задач используй два прохода исправлений и один повтор критика, если утверждённый план не требует меньшего бюджета. Старые контракты не переписывай. По умолчанию исполнитель — `gpt-5.6-sol` с `high`; для планирования и зафиксированной эскалации используй `gpt-6-astra`. Ведущий передаёт модель и уровень рассуждения явно при создании нативного исполнителя. Эти поля — постановка, а не подтверждение MCP о фактически запущенной модели.

Поля `dependencies` и `wave` задают порядок локальной реализации. `dependency_strategy: parallel | stacked | after_merge` задаёт порядок публикации PR; `after_merge` не означает, что локально готовая задача должна ждать внешнего слияния. Интеграционная задача получает `role: integration` и `report_only`.

Первой исследовательской задачей вида `analysis` проверь фактическую доступность нужной среды исполнения, диспетчера пакетов, реестров, контейнеров, внешних сервисов, закреплённых контрактов и моделей. Проверяй ресурс, а не VPN или другой предполагаемый механизм доступа. Операционный сбой получает `blocked` или `interrupted`; `needs_human` нужен лишь для реального пользовательского решения или действия.

## Выполнение по волнам

Создай отдельное чистое рабочее дерево для каждого готового исполнителя. Передай ему закрытый снимок спеки, полный контракт задачи, базу, пути и проверки. Запускай через `spawn_agent` с `fork_turns: "none"`, `model: execution.native_model` и `reasoning_effort: execution.reasoning_effort`. Одновременно работают не более трёх исполнителей; оставляй место для независимого проверяющего.

В постановке исполнителю явно передай уже данное разрешение: ссылку на сообщение пользователя, его точную разрешающую фразу, репозиторий/задачу, разрешённые локальные действия, согласованный subject коммита (если есть) и оставшиеся запреты. Это подтверждение существующего разрешения, а не новое разрешение от ведущего. Не проси пользователя повторять его для того же действия. Если среда отклонила команду, не меняй её формулировку ради обхода: передай отказ ведущему для проверки области и штатного запроса разрешений среды. При отсутствии доказанного разрешения коммит не выполняется.

Для каждой реализации:

1. Переведи задачу в `in_progress` и вызови `create_run` со ссылкой на кампанию. Связанный прогон сохраняет цель задачи и наследует критерии, ограничения, нецели, запрещённые действия, проверки, ссылки, настройки и бюджеты. Он может добавить критерии, ограничения, нецели, запрещённые действия и проверки, но не может переопределить одноимённую проверку или зафиксированную настройку.
2. Исполнитель реализует один срез, измеряет изменение, создаёт согласованный атомарный коммит и запускает проверки полного результата от замороженной базы.
3. Свежий Claude проверяет результат. После допустимого временного сбоя можно один раз явно повторить критика, назвав неудачный этап. После исправлений используй [повторное ревью](../../workflow/references/review-followups.md): актуальные проверки обязательны, повторный критик проверяет исправления и затронутые связи; узкое несемантическое P3-завершение сохраняет исходное ревью без новой модели.
4. Только `terminal complete` связывается с задачей через `record_campaign_task`. Исполнитель возвращает `run_id`, SHA коммита и короткий итог.

Перед вторым и последующими прогонами в общем рабочем дереве проверь, что все уже изменённые пути принадлежат завершённым задачам этой кампании, и только тогда передай `allow_dirty: true`. Не применяй это разрешение к исходным пользовательским изменениям.

Независимые задачи одной волны репозитория могут начинаться от общей базы при непересекающихся ожидаемых путях. Если волна объединяет несколько срезов, добавь интеграционную задачу `kind: implementation`, `role: integration`. Её исполнитель закрепляет идентификаторы и SHA, объединяет коммиты через согласованный `git merge --no-ff`, проверяет `git merge-base --is-ancestor <sha> HEAD`, затем запускает полные проверки и отдельное ревью. Следующая волна использует этот коммит через `base_from_task`. Если срез в волне один, её следующий исполнитель использует точный SHA завершённой исходной задачи напрямую, без интеграционного коммита и повторного ревью идентичного дерева. Новая политика `combined-review-when-needed` не меняет старые кампании с `combined-review-required`.

Если пути неожиданно пересеклись, разреши однозначный технический конфликт внутри утверждённого поведения. Спроси пользователя только когда варианты меняют продукт или область либо невозможно определить намерение в пользовательских изменениях. После `blocked`, `failed` или `interrupted` создай новый прогон для того же идентификатора задачи; один `run_id` нельзя связывать с несколькими задачами.

Общий период блокировки Anthropic сохраняется. `anthropic_limit` разрешает только явно помеченный `codex_fallback` и одну позднюю пробу после окончания периода. `transient_timeout` или `transient_process_failure` разрешает один новый этап по одноразовому бюджету: вызови `start_stage` с `retry_stage_id` неудачного этапа. Повтор того же запроса идемпотентен. Отмена, аутентификация, оплата, безопасность, невалидный результат и запрет модели не разрешают повтор или резервного проверяющего.

`needs_human` допустим только после `record_campaign_intervention` с неразрешённым блокирующим вмешательством. Операционный сбой завершай как `blocked` или `interrupted`.

## Завершение и публикация

После всех задач снова проверь OpenSpec, затем вызови `seal_campaign_candidate` до дополнительных правок и `finish_campaign(status: complete)`. Для параллельной работы итогом репозитория служит интеграционное дерево; исходные деревья сохраняют происхождение изменений.

Публикацию готовь в текущей пользовательской задаче: ведущий не создаёт следующую задачу, если пользователь явно не выбрал отдельный контекст. Для самостоятельного PR достаточно завершённого прогона; для общего PR дождись завершения интеграции. В обоих случаях установи `publication_context` по [единому формату](../../delivery-writing/references/publication-context.md), включи `scope_id`, все `source_run_ids` и отдельную запись каждого кандидата в `candidates`. Проверь через Agent Harness и Git состояние, полное изменение, пути, актуальные проверки и текущее ревью каждого кандидата. Одно расхождение останавливает весь пакет.

Покажи описание сделанного, размеры, локальную ручную проверку, коммит, PR-текст, рекомендации к тестированию и точный список действий. Однозначная команда пользователя разрешает только названную часть показанного пакета. Уже данное разрешение сохраняется для неизменившейся обратимой операции и её повторения после временного сбоя. Отправка ветки, PR, Jira, слияние, развёртывание, миграция и другие внешние действия не следуют из локальной готовности.
