# Обычный путь эпика

## Сбор исходных данных

1. Прочитай эпик в Jira, его дочерние задачи, связи, актуальные комментарии и открытые вопросы. Не делай вывод о составе работ только по заголовку.
2. Для каждой затронутой кодовой базы проверь `AGENTS.md`, `CLAUDE.md`, текущее состояние Git, активные PR и проверки. В `<repository-host>` используй GitHub Enterprise MCP для метаданных и локальный `git` для кода.
3. Отдели наблюдаемый результат и продуктовый контракт от исторических деталей реализации. Не переноси в новую задачу случайное устройство старого кода, если оно не является ограничением.

## Локальная декомпозиция

Составь задачи в формате `delivery-writing`: короткий Jira-заголовок, раздел `Что сделать`, точный результат, границы и критерии готовности. На этом этапе не пиши окончательные рекомендации к тестированию — они появятся после фактической реализации.

Оставь только задачи, которые дают самостоятельный проверяемый результат. Укажи зависимость только от более ранней задачи. Для каждой задачи выбери один вид:

- `implementation` — меняет репозиторий и обязана завершиться отдельным v1 run;
- `analysis` — закрывает архитектурный или продуктовый вопрос без правки кода;
- `delivery` — готовит итоговые материалы после реализации.

В чистом координирующем рабочем дереве вызови `create_campaign` с режимом `delivery`, источником Jira или локальным черновиком и полным упорядоченным списком задач. Для каждой `implementation`-задачи зафиксируй корень её рабочего дерева и `base_sha`. Jira остаётся системой учёта, но кампания хранит только очищенный локальный контракт.

## Выполнение

Для каждого репозитория используй одно изолированное рабочее дерево кампании от зафиксированного `base_sha`; не раскладывай последовательные задачи одного репозитория по независимым рабочим деревьям. Накапливай изменения без промежуточных коммитов до `seal_campaign_candidate`. Перед вторым и последующими прогонами v1 проверь, что все уже изменённые пути принадлежат завершённым задачам этой кампании, и только тогда передай `allow_dirty: true`. Не применяй это разрешение к исходным пользовательским изменениям.

1. Переведи очередную готовую задачу в `in_progress` через `record_campaign_task`.
2. Для `implementation` проведи изменение через `workflow` в рабочем дереве кампании, заверши проверки и независимое ревью. Только после `complete` прогона v1 запиши задачу как `complete` с `run_workspace` и `run_id`.
3. Для `analysis` и `delivery` сохрани короткий итог без сырого вывода внешних инструментов.
4. При реальной развилке задай один объединённый вопрос и запиши очищенную причину через `record_campaign_intervention`. После ответа отметь ту же запись как разрешённую.
5. Не начинай зависимую задачу, пока предыдущая не завершена.

После `blocked`, `failed` или `interrupted` повторно переведи задачу в `in_progress` и создай новый прогон v1. Один `run_id` нельзя использовать для нескольких задач.

После всех задач, до дополнительных правок и коммитов, вызови `seal_campaign_candidate`: он зафиксирует Git-снимок и отклонит пути, не покрытые завершёнными прогонами v1. Затем вызови `finish_campaign(status: complete)`. Из фактических изменений и проверок подготовь рекомендации к тестированию и короткие описания PR через `delivery-writing`. Покажи тексты пользователю до любых изменений Jira или GitHub.
