# Обычный путь эпика

## Сбор исходных данных

1. Прочитай эпик в Jira, его дочерние задачи, связи, актуальные комментарии и открытые вопросы. Не делай вывод о составе работ только по заголовку.
2. Для каждой затронутой кодовой базы проверь `AGENTS.md`, `CLAUDE.md`, текущее состояние Git, активные PR и проверки. В `<repository-host>` используй GitHub Enterprise MCP для метаданных и локальный `git` для кода.
3. Отдели наблюдаемый результат и продуктовый контракт от исторических деталей реализации. Не переноси в новую задачу случайное устройство старого кода, если оно не является ограничением.

## Локальная декомпозиция

Составь задачи в формате `delivery-writing`: короткий Jira-заголовок, раздел `Что сделать`, точный результат, границы и критерии готовности. На этом этапе не пиши окончательные рекомендации к тестированию — они появятся после фактической реализации.

Для крупной идеи, неоднозначного или высокорискового изменения, эпика с несколькими задачами либо одной задачи со сложным поведением используй обязательный [слой OpenSpec](openspec.md). Без отдельной спеки продолжай только для узкой однозначной задачи, не меняющей поведение параллелизма, повторов, частичных отказов, согласованности или нескольких внешних интеграций.

Оставь только задачи, которые дают самостоятельный проверяемый результат. Задача реализации должна содержать одну функциональность: законченный вертикальный срез, который можно отдельно собрать, проверить, опубликовать и при необходимости откатить. Не дели одну операцию по слоям, файлам или пакетам и не отделяй от неё инварианты безопасности и согласованности. Укажи зависимость только от более ранней задачи. Для каждой задачи выбери один вид:

- `implementation` — меняет репозиторий и обязана завершиться отдельным v1 run;
- `analysis` — закрывает архитектурный или продуктовый вопрос без правки кода;
- `delivery` — после реализации собирает только компактный пакет передачи для будущей пользовательской задачи публикации; не пишет окончательные тексты и ничего не публикует.

Для обычного среза целься в 300–700 изменённых строк рабочего кода. Нижнего ограничения нет: маленькую правку конфигурации не расширяй искусственно. Тесты, документацию, конфигурацию, сгенерированные и бинарные файлы оценивай отдельно. Если ожидается больше 700 строк, проверь, не соединены ли несколько независимо полезных поведений. Связный срез оставь целым и кратко объясни в `exception_reason`, какое промежуточное состояние перестанет собираться, проверяться, безопасно выкатываться или откатываться. Сам размер, общий эпик и уже написанный общий diff таким объяснением не являются; высокий риск только из-за размера не назначай.

Если срез даёт самостоятельный продуктовый результат, создай для него отдельную Jira-задачу. Если деление требуется только для удобного ревью, несколько локальных задач и PR могут остаться в одной Jira-задаче. Для зависимых PR явно выбери `parallel`, `stacked` или `after_merge`: последний вариант используй для несовместимых контрактов, миграций и порядка развёртывания. Интеграционный прогон проверяет объединённый результат в режиме `report_only`, но не создаёт общий PR сам по себе.

Задачу с несколькими самостоятельно выпускаемыми операциями разумно делить по этим операциям. Обновление версии PHP, которое невозможно собрать в промежуточном состоянии, допустимо оставить одним изменением.

В чистом координирующем рабочем дереве вызови `create_campaign` с режимом `delivery`, источником Jira или локальным черновиком и полным упорядоченным списком задач. Локальный `/openspec` должен быть исключён Git и поэтому не загрязняет дерево. Только явный `storage: repository` разрешает незакоммиченные пути внутри выбранного `openspec/changes/<change-id>/`. Для каждой `implementation`-задачи зафиксируй корень её рабочего дерева, `base_sha` и `review_budget`; по умолчанию это диапазон `0..700`, мягкий предел 700 и пустой `exception_reason`. Jira остаётся системой учёта, но кампания хранит только очищенный локальный контракт.

Первой `analysis`-задачей кампании выполни предварительный пункт `tasks.md`: проверь фактическую готовность окружения всех репозиториев, версии runtime и package manager, доступ к нужным registry, контейнерам и внешним зависимостям. Не требуй VPN как таковой. Если доступ уже есть из офисной или другой сети, проверка зелёная.

Последовательные задачи одного репозитория завершаются чистыми атомарными локальными коммитами; следующая использует `base_from_task`, поэтому её проверки и ревью видят только собственный diff. Если независимые задачи пойдут параллельно, они образуют последний блок реализации этого репозитория и работают в отдельных рабочих деревьях от одного `base_sha`. Для двух и более задач репозитория всегда добавь итоговую `implementation`-задачу с `role: integration`: она зависит от всех реализаций, смотрит объединённый diff от исходной базы и проходит проектные проверки и собственное ревью. В план включи точные сообщения исходных и интеграционных коммитов.

## Выполнение

Последовательную задачу одного репозитория начинай от коммита `base_from_task` и завершай согласованным атомарным локальным коммитом до запуска следующей. Независимые задачи с непересекающимися областями изменений можно отдать отдельным исполнителям в отдельных рабочих деревьях от того же `base_sha`. Каждый исполнитель сначала вызывает `create_run`, вносит изменения и вызывает `measure_diff` после законченного среза, а также перед добавлением следующего поведения, когда объём приближается к 500 строкам. Статус `over_soft_limit` не блокирует проверки или ревью: исполнитель повторно сверяет функциональную цель, уменьшает срез, если в нём несколько поведений, либо продолжает связное изменение и сохраняет объяснение для публикации. Затем он создаёт согласованный локальный коммит, планирует проверки и проходит ревью; возможную корректировку добавляет в тот же коммит до повторных проверок. Перед вторым и последующими прогонами v1 в общем рабочем дереве проверь, что все уже изменённые пути принадлежат завершённым задачам этой кампании, и только тогда передай `allow_dirty: true`. Не применяй это разрешение к исходным пользовательским изменениям.

1. Переведи все готовые задачи в `in_progress` через `record_campaign_task` и запусти для каждой отдельного исполнителя, но держи одновременно не более трёх исполнителей.
2. Для `implementation` сначала передай в `create_run` ссылку на кампанию. Исполнитель до финальных проверок создаёт согласованный атомарный локальный коммит; после одной корректировки изменяет тот же коммит и повторяет проверки. Только после `complete` прогона v1 запиши задачу как `complete` с `run_workspace` и `run_id`. Если это самостоятельная Jira-задача с собственным PR, ведущий сразу создаёт для неё задачу публикации и продолжает остальные работы кампании. Передача допустима только из отдельной ветки либо изолированного рабочего дерева, которое больше не меняют активные прогоны. Для нескольких реализаций в одном PR дождись только `complete` интеграционной задачи.
3. Для `analysis` сохрани короткий итог без сырого вывода внешних инструментов. Для `delivery` собери только пакет передачи: фактические SHA и ветки, изменённые пути, проверки, ревью, остаточные риски и ещё не разрешённые действия.
4. При реальной развилке задай один объединённый вопрос и запиши очищенную причину через `record_campaign_intervention`. Внешнее действие пользователя помечай `external_unblock`. Обычный запрос статуса и переход задачи в `blocked` или `interrupted` не являются вмешательством. `needs_human` ставь только после записи неразрешённого блокирующего вмешательства.
5. Не начинай зависимую задачу, пока предыдущая не завершена.

Для интеграционной задачи сначала вызови `create_run` в чистом рабочем дереве с унаследованным бюджетом в режиме `report_only`. Заморозь в его контракте идентификаторы исходных задач и SHA коммитов, затем влей каждый коммит через `git merge --no-ff` с согласованным сообщением. Обязательные проверки интеграционного прогона должны включать `git merge-base --is-ancestor <sha> HEAD` для каждого исходного SHA. Если фактические области изменений пересеклись, разрешай конфликт только при однозначном продуктовом результате; иначе задай один вопрос. Объединённый результат обязан получить все проектные проверки и собственное ревью до статуса `complete`, но не считается отдельным продуктовым PR.

После `blocked`, `failed` или `interrupted` повторно переведи задачу в `in_progress` и создай новый прогон v1. Один `run_id` нельзя использовать для нескольких задач.

После всех задач, до дополнительных правок, вызови `seal_campaign_candidate`: он зафиксирует Git-снимки и отклонит пути, не покрытые завершёнными прогонами v1. Для параллельного репозитория итоговым результатом считай снимок интеграционного рабочего дерева; рабочие деревья отдельных задач остаются проверяемыми промежуточными результатами. Затем вызови `finish_campaign(status: complete)`.

Для каждого самостоятельного PR или Jira-результата ведущий создаёт отдельную видимую задачу публикации без истории реализации, в текущем Codex app — через `create_thread`, только если это было указано в согласованном плане. Не используй `fork_thread`. Если создание свежей задачи недоступно, покажи компактный пакет передачи и попроси пользователя открыть её вручную, не выполняя внешних записей. Создавай задачу сразу после `complete` соответствующей реализации либо интеграционного прогона для общего PR; не жди `seal_campaign_candidate` или `finish_campaign`. Если создание не было согласовано заранее, один раз спроси пользователя и до ответа оставайся в текущем чате без внешних записей.

Передай новой задаче только ссылку на Jira или локальный источник, рабочие каталоги кампании и прогона, `campaign_id`, ID задачи, `run_id`, текущий `diff_fingerprint`, `diff_stats`, `budget_status`, репозиторий и изолированное рабочее дерево кандидата, базовый и итоговый SHA, ветку, remote, целевую ветку PR, краткое описание сделанного, изменённые пути, результаты проверок, итог независимого ревью, остаточные риски и перечень ещё не разрешённых внешних действий. Не передавай полный чат, сырой diff, журналы команд или отчёт модели. Новая задача сначала вызывает `get_run` и `get_campaign`, сверяет `complete`, отпечаток diff, зелёные проверки, закрытое ревью и принадлежность путей, а затем сама читает фактический diff от базового SHA. Любое расхождение останавливает подготовку пакета и возвращает кандидата в контекст реализации. Через `delivery-writing` задача готовит описание сделанного, короткое описание PR и полный блок рекомендаций к тестированию, показывает точный пакет публикации и ждёт `публикуем` для перечисленных в нём действий.

После публикации продолжай в той же задаче публикации: проверяй CI, обрабатывай замечания ревью, следи за состоянием развёртывания и разбирай его сбои. Если нужен кодовый фикс, запусти из этого контекста новый `workflow`; не создавай ещё одну видимую задачу. Само развёртывание, миграция и другие внешние действия по-прежнему требуют отдельного явного разрешения.
