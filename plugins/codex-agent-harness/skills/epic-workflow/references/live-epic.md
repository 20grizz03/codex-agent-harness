# Обычный путь эпика

## Сбор исходных данных

1. Прочитай эпик в Jira, его дочерние задачи, связи, актуальные комментарии и открытые вопросы. Не делай вывод о составе работ только по заголовку.
2. Для каждой затронутой кодовой базы проверь `AGENTS.md`, `CLAUDE.md`, текущее состояние Git, активные PR и проверки. В `<repository-host>` используй GitHub Enterprise MCP для метаданных и локальный `git` для кода.
3. Отдели наблюдаемый результат и продуктовый контракт от исторических деталей реализации. Не переноси в новую задачу случайное устройство старого кода, если оно не является ограничением.

## Локальная декомпозиция

Составь задачи в формате `delivery-writing`: короткий Jira-заголовок, раздел `Что сделать`, точный результат, границы и критерии готовности. На этом этапе не пиши окончательные рекомендации к тестированию — они появятся после фактической реализации.

Для крупной идеи, неоднозначного изменения, высокого риска или эпика с несколькими задачами используй обязательный [слой OpenSpec](openspec.md). Для одной готовой Jira-задачи продолжай без отдельной спеки.

Оставь только задачи, которые дают самостоятельный проверяемый результат. Укажи зависимость только от более ранней задачи. Для каждой задачи выбери один вид:

- `implementation` — меняет репозиторий и обязана завершиться отдельным v1 run;
- `analysis` — закрывает архитектурный или продуктовый вопрос без правки кода;
- `delivery` — готовит итоговые материалы после реализации.

В чистом координирующем рабочем дереве вызови `create_campaign` с режимом `delivery`, источником Jira или локальным черновиком и полным упорядоченным списком задач. Исключение — согласованный OpenSpec change: его собственные файлы могут оставаться незакоммиченными, если в дереве нет других изменений. Для каждой `implementation`-задачи зафиксируй корень её рабочего дерева и `base_sha`. Jira остаётся системой учёта, но кампания хранит только очищенный локальный контракт.

Первой `analysis`-задачей кампании выполни предварительный пункт `tasks.md`: проверь фактическую готовность окружения всех репозиториев, версии runtime и package manager, доступ к нужным registry, контейнерам и внешним зависимостям. Не требуй VPN как таковой. Если доступ уже есть из офисной или другой сети, проверка зелёная.

Последовательные задачи одного репозитория завершаются чистыми атомарными локальными коммитами; следующая использует `base_from_task`, поэтому её проверки и ревью видят только собственный diff. Если независимые задачи пойдут параллельно, они образуют последний блок реализации этого репозитория и работают в отдельных рабочих деревьях от одного `base_sha`. Для двух и более задач репозитория всегда добавь итоговую `implementation`-задачу с `role: integration`: она зависит от всех реализаций, смотрит объединённый diff от исходной базы и проходит проектные проверки и собственное ревью. В план включи точные сообщения исходных и интеграционных коммитов.

## Выполнение

Последовательную задачу одного репозитория начинай от коммита `base_from_task` и завершай согласованным атомарным локальным коммитом до запуска следующей. Независимые задачи с непересекающимися областями изменений можно отдать отдельным исполнителям в отдельных рабочих деревьях от того же `base_sha`. Каждый исполнитель сначала вызывает `create_run`, вносит изменения, создаёт согласованный локальный коммит, затем планирует проверки и проходит ревью; возможную корректировку добавляет в тот же коммит до повторных проверок. Перед вторым и последующими прогонами v1 в общем рабочем дереве проверь, что все уже изменённые пути принадлежат завершённым задачам этой кампании, и только тогда передай `allow_dirty: true`. Не применяй это разрешение к исходным пользовательским изменениям.

1. Переведи все готовые задачи в `in_progress` через `record_campaign_task` и запусти для каждой отдельного исполнителя, но держи одновременно не более трёх исполнителей.
2. Для `implementation` сначала передай в `create_run` ссылку на кампанию. Если на результат ссылается `base_from_task`, исполнитель до финальных проверок создаёт согласованный атомарный локальный коммит; после одной корректировки изменяет тот же коммит и повторяет проверки. Только после `complete` прогона v1 запиши задачу как `complete` с `run_workspace` и `run_id`.
3. Для `analysis` и `delivery` сохрани короткий итог без сырого вывода внешних инструментов.
4. При реальной развилке задай один объединённый вопрос и запиши очищенную причину через `record_campaign_intervention`. Внешнее действие пользователя помечай `external_unblock`. Обычный запрос статуса и переход задачи в `blocked` или `interrupted` не являются вмешательством. `needs_human` ставь только после записи неразрешённого блокирующего вмешательства.
5. Не начинай зависимую задачу, пока предыдущая не завершена.

Для интеграционной задачи сначала вызови `create_run` в чистом рабочем дереве. Заморозь в его контракте идентификаторы исходных задач и SHA коммитов, затем влей каждый коммит через `git merge --no-ff` с согласованным сообщением. Обязательные проверки интеграционного прогона должны включать `git merge-base --is-ancestor <sha> HEAD` для каждого исходного SHA. Если фактические области изменений пересеклись, разрешай конфликт только при однозначном продуктовом результате; иначе задай один вопрос. Объединённый результат обязан получить все проектные проверки и собственное ревью до статуса `complete`.

После `blocked`, `failed` или `interrupted` повторно переведи задачу в `in_progress` и создай новый прогон v1. Один `run_id` нельзя использовать для нескольких задач.

После всех задач, до дополнительных правок, вызови `seal_campaign_candidate`: он зафиксирует Git-снимки и отклонит пути, не покрытые завершёнными прогонами v1. Для параллельного репозитория итоговым результатом считай снимок интеграционного рабочего дерева; рабочие деревья отдельных задач остаются проверяемыми промежуточными результатами. Затем вызови `finish_campaign(status: complete)`. Из фактических изменений и проверок подготовь рекомендации к тестированию и короткие описания PR через `delivery-writing`. Покажи тексты пользователю до любых изменений Jira или GitHub.
