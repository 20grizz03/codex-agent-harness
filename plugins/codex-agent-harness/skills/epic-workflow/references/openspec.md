# Слой OpenSpec

OpenSpec хранит согласуемый продуктовый и технический контракт в `/openspec` целевого проекта. Agent Harness хранит исполнение, проверки и ревью.

## Когда использовать

Используй OpenSpec для крупной, неоднозначной, высокорисковой или многозадачной работы, а также для одной задачи, меняющей параллелизм, повторы и восстановление, частичный отказ, идемпотентность, согласованность, безопасность данных, совместимость либо несколько внешних интеграций. Количество Jira-задач и размер изменения не заменяют эту оценку.

Если пользователь уже дал эквивалентный подробный план и попросил его выполнить, материализуй артефакты без повторного запроса подтверждения. Обращайся к пользователю только при новом продуктовом решении или изменении области. Внутренние структуры, имена методов и другие технические решения ведущий выбирает сам в границах утверждённого контракта.

## Хранение и CLI

Проверь `openspec` в `PATH`. Если CLI отсутствует, подготовь локальный черновик и останови только зависящее от него выполнение; установку пользователь подтверждает отдельно. Все команды запускай с `OPENSPEC_TELEMETRY=0`.

Обычный режим — `local`. Если `git ls-files -- openspec` возвращает пути или команда явно версионирует спеки, используй `storage: repository`. Для локального режима добавь `/openspec/` в `.git/info/exclude`, если точного правила ещё нет, и проверь `git check-ignore`. Это обратимая подготовка уже согласованной работы и не требует повторного разрешения. Не запускай `openspec init` для локального режима.

Проверь схему через `openspec schema which agent-harness`, создай change со схемой `agent-harness`, затем получай актуальные инструкции через `openspec instructions <artifact> --change <change-id>`. Не сохраняй сырой вывод CLI в кампании.

## Артефакты и практическая готовность

До показа пользователю проверь полный набор артефактов и согласованность статуса готовности.

1. В `proposal.md` зафиксируй цель, наблюдаемые изменения, исключения, влияние и только настоящие продуктовые вопросы.
2. В `specs/` опиши требования и сценарии MUST/WHEN/THEN, включая применимые ошибки, безопасность, восстановление, совместимость и эксплуатацию.
3. В `design.md` опиши существенные решения и обязательно заполни Security and Data, Failure and Recovery, Operability, Compatibility, UI and Source Material и Decomposition Readiness.
4. В `tasks.md` перенеси готовность и сделай явную таблицу или список покрытия «требование → задача → сценарий/проверка». Требование не готово к реализации без задачи; задача не готова без проверяемого сценария.
5. Для каждого внешнего или межкомпонентного контракта укажи стабильную ссылку и закреплённую версию. Приложи контракт к доступному снимку или убедись, что исполнитель может разрешить ссылку. В предварительной задаче проверь доступность фактической версии.
6. Для каждой задачи вида `implementation` укажи одну функциональность, результат, границы, ожидаемый объём рабочего кода, отдельный объём тестов, зависимости, волну, Jira, PR, стратегию публикации и проверки.

В сценарии включи применимые границы: первый запуск, пустые/некорректные данные, конкурентное обновление, заполнение ресурсов, частичный отказ, отмену и предельную задержку. Укажи ожидаемый результат и способ проверки, не добавляя в продукт неприменимые механизмы.

В `design.md` используй точный заголовок `## Decomposition Readiness` и строку `Статус: ready`; в начале `tasks.md` повтори `Статус: ready`. Статус означает, что известны компоненты, репозитории, владельцы, закреплённые контракты, состояния, ошибки, восстановление, совместимость, миграции, порядок внедрения, публикация и откат; покрытие требований полное; ссылки доступны. Оставшиеся технические решения не должны менять состав и зависимости задач. Иначе в обоих файлах укажи `Статус: analysis_required`, оставь отдельную исследовательскую задачу вида `analysis` и не создавай приблизительную декомпозицию реализации.

Ориентир — 300–700 изменённых строк рабочего кода, без нижнего ограничения. Тесты, документацию, конфигурацию, сгенерированные и бинарные файлы оценивай отдельно. Превышение допустимо для связного среза с `exception_reason`. Сам размер не блокирует готовность.

## Волны и публикационный порядок

`dependencies` и `wave` описывают локальный граф выполнения. Независимые задачи волны могут работать от общей базы в отдельных деревьях. При объединении нескольких срезов волны добавь `kind: implementation`, `role: integration`: она зависит от задач волны, объединяет их коммиты, запускает полные проверки и независимое ревью. Следующая волна использует её коммит как `base_from_task`. Если в волне один срез, следующий использует точный проверенный SHA этой завершённой задачи напрямую; отдельный прогон для идентичного дерева не нужен. Не переписывай уже замороженную кампанию ради смены политики.

`dependency_strategy` описывает публикацию:

- `parallel` — PR можно публиковать независимо;
- `stacked` — PR образуют локально проверяемую последовательность;
- `after_merge` — внешний выпуск ждёт слияния зависимости.

`after_merge` не является локальной зависимостью и не требует откладывать реализацию готовой задачи. Интеграционный прогон получает `report_only` и не считается отдельным продуктовым PR.

## Проверка и кампания

Перед `create_campaign` выполни:

```text
env OPENSPEC_TELEMETRY=0 openspec validate <change-id> --strict --no-interactive
```

Для локального режима передай `{"kind":"openspec","change_id":"<change-id>"}`. Сервер проверит исключение Git, вычислит семантический SHA-256, сохранит закрытый снимок и добавит в связанные прогоны закреплённую ссылку `{ref: "openspec:<change-id>", revision: "<sha256>"}`. Состояние флажков в `tasks.md` не входит в отпечаток; другое содержательное изменение блокирует переходы.

Для явного версионируемого режима добавь `"storage":"repository"`. Незакоммиченные пути спеки тогда ограничены выбранным `openspec/changes/<change-id>/`.

Исполнители читают замороженную спеку, но не редактируют общий `tasks.md`. Ведущий отмечает пункт только после завершения связанного прогона. Изменение смысла спеки требует нового подтверждения и кампании; техническое решение внутри её границ и отметка выполнения не требуют.

После всех задач снова строго проверь изменение OpenSpec. В локальном режиме не архивируй его: запечатай кампанию с актуальным `/openspec`. Только `storage: repository` использует отдельный прогон `openspec-finalize`, который проверяет отметки, валидирует и архивирует изменение, включает архив в собственное изменение Git, проходит проверки и ревью, а затем связывается со служебной задачей. `--skip-specs` допустим только для явно описанного рефакторинга, инструментария или документации без изменения поведения.
