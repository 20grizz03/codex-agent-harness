# Слой OpenSpec

OpenSpec хранит согласуемую спеку в `/openspec` целевого проекта, а Agent Harness остаётся единственным журналом исполнения. `tasks.md` описывает план; статусы кампании, проверки и ревью живут только в Agent Harness.

## Когда использовать

Используй OpenSpec для активной крупной идеи, неоднозначного или высокорискового изменения, эпика с несколькими задачами и для одной задачи, которая меняет параллелизм, повторы и восстановление, частичный успех или отказ, идемпотентность, согласованность, безопасность данных, совместимость либо несколько внешних интеграций. Для такого изменения утверждённая спека обязательна до реализации, но по умолчанию не входит в Git. Не используй OpenSpec для слепого контрольного прогона закрытого эпика и для узкой однозначной правки без этих границ.

Количество задач и длина плана не являются критерием. Например, независимый запуск Google, Facebook и Yandex с повторами, сохранением частичного успеха, агрегированными ошибками и метриками — одна Jira-задача, но обязательный OpenSpec. Если пользователь уже дал эквивалентный подробный план и попросил его выполнить, материализуй и покажи артефакты без повторного запроса подтверждения; остановись только при новом продуктовом решении или изменении контракта.

Сначала проверь `openspec` в `PATH`. Если CLI отсутствует, подготовь локальный черновик и остановись до реализации: установку зависимости пользователь подтверждает отдельно. Не запускай `openspec init`, если он может менять файлы вне `/openspec`.

Во всех вызовах CLI отключай телеметрию через `env OPENSPEC_TELEMETRY=0 openspec ...`.

## Хранение

Обычный режим — `local`. Сначала выполни `git ls-files -- openspec`: если вывод не пуст или пользователь явно решил хранить спеки в Git, не меняй правила исключения и используй `storage: repository`; только этот режим включает версионируемую архивацию и задачу `openspec-finalize`.

Для неотслеживаемого `/openspec` проверь `.gitignore` и путь из `git rev-parse --git-path info/exclude`. Если правило ещё не действует, один раз добавь точную строку `/openspec/` в локальный `info/exclude`; это входит в подготовку уже согласованной декомпозиции и не требует отдельного подтверждения. Не дублируй правило. После создания файлов проверь `git check-ignore --quiet -- openspec/config.yaml` и `.openspec.yaml` выбранного change. Сервер повторит проверку.

## Подготовка спеки

1. Прочитай существующие `openspec/specs/` и код, чтобы не создать параллельный контракт на уже описанное поведение.
2. Проверь `env OPENSPEC_TELEMETRY=0 openspec schema which agent-harness`. Для нового локального каталога создай `openspec/config.yaml` со схемой `agent-harness`, затем создай change через `env OPENSPEC_TELEMETRY=0 openspec new change <change-id> --schema agent-harness`. В явном `repository`-режиме сохраняй уже выбранную командой схему; не подменяй её автоматически.
3. Получай актуальные указания через `env OPENSPEC_TELEMETRY=0 openspec instructions <artifact> --change <change-id>` и заполняй артефакты по порядку. Не сохраняй сырой вывод CLI в состоянии кампании.
4. В `proposal.md` зафиксируй цель, изменения, исключения, влияние и открытые продуктовые вопросы. В `specs/` описывай наблюдаемое поведение, состояния, ошибки и проверяемые сценарии без деталей классов и функций. В `design.md` обязательно закрой безопасность и данные, отказ и восстановление, эксплуатацию, совместимость, UI и исходные материалы; неприменимое отметь с причиной. Каждый пункт `tasks.md` должен содержать одну функциональность и указывать наблюдаемый результат, endpoints или функции, границы, ожидаемый объём рабочего кода, отдельный объём тестирования, зависимости, Jira-задачу, соответствующий PR и способ проверки.
5. Нерешённый вопрос, меняющий требования, архитектурное решение или декомпозицию, вынеси пользователю до выполнения. Вопрос, который безопасно решить во время реализации, оставь явным в спеке.
6. Не добавляй окончательные рекомендации к тестированию: они формируются после реализации из фактического изменения.

Пользователь должен увидеть полный набор артефактов и один раз подтвердить план до кода. Уже переданный пользователем конкретный план с просьбой выполнить его считается подтверждённым.

Декомпозируй по вертикальным срезам, которые отдельно собираются, проверяются, публикуются и откатываются. Обычный ориентир — 300–700 изменённых строк рабочего кода без нижнего ограничения; тесты, документацию, конфигурацию, сгенерированные и бинарные файлы оценивай отдельно. Превышение 700 строк само по себе не блокирует задачу. Для заранее ожидаемого превышения запиши `exception_reason`, объясняющий невозможность безопасного разделения. Для зависимых PR укажи стратегию `parallel`, `stacked` или `after_merge`. Интеграционный пункт получает `report_only`, проверяет объединённый результат и сам по себе не является PR.

Первым пунктом `tasks.md` сделай предварительную проверку всех реально нужных возможностей: версий runtime, package manager, доступа к registry, контейнеров и внешних зависимостей. Проверяй сам доступ, а не наличие VPN: в офисной сети тот же ресурс может быть доступен напрямую. Недоступная возможность переводит пункт в `blocked`; `needs_human` используй только если действительно требуется действие или решение пользователя.

Перед `create_campaign` выполни:

```text
env OPENSPEC_TELEMETRY=0 openspec validate <change-id> --strict --no-interactive
```

Передай в кампанию только:

```json
{"kind":"openspec","change_id":"<change-id>"}
```

В локальном режиме отсутствие `storage` означает `local`. Сервер требует Git ignore, вычисляет семантический SHA-256, сохраняет закрытый снимок в общих Git-метаданных и сверяет снимок с проектным `/openspec` перед переходами задач и запечатыванием результата. Состояние checkbox в `tasks.md` в отпечаток не входит. Папка `/openspec` не должна появляться в `git status`; любое другое изменение сохраняет обычную остановку по грязному дереву.

Для явного версионируемого режима передай:

```json
{"kind":"openspec","change_id":"<change-id>","storage":"repository"}
```

В этом режиме незакоммиченная спека может содержать только пути внутри выбранного `openspec/changes/<change-id>/`.

## Выполнение и завершение

Исполнители читают замороженную спеку, но не редактируют общий `tasks.md`. Ведущий отмечает пункт выполненным только после `record_campaign_task(..., status: complete)` соответствующего прогона.

Изменение смысла утверждённой спеки требует нового подтверждения и новой кампании. Исправление опечатки или отметка выполнения не меняет продуктовый контракт.

В локальном режиме после выполнения пунктов снова строго проверь change, затем запечатывай кампанию. Не добавляй `openspec-finalize` и не архивируй локальную спеку: её итоговое состояние остаётся в `/openspec`, а исполнение — в Agent Harness.

Для последовательных задач одного репозитория каждая задача после первой использует `base_from_task` и начинается от чистого атомарного коммита предшественника. Для двух и более задач добавь отдельную задачу с `role: integration`: она зависит от всех реализаций, смотрит объединённый diff от исходной базы и проходит полный набор проверок и собственное независимое ревью.

Только для `storage: repository` после `terminal complete` всех задач из `tasks.md` ведущий отмечает их пункты и запускает для `openspec-finalize` отдельный v1 `workflow`:

1. убедиться, что все пункты `tasks.md` отмечены;
2. снова запустить строгую проверку change;
3. выполнить `env OPENSPEC_TELEMETRY=0 openspec archive <change-id> -y`;
4. включить изменённые основные спеки и архивный каталог в diff этого прогона;
5. выполнить `plan_checks`, проектные проверки и независимое ревью;
6. после `terminal complete` связать прогон со служебной задачей и только затем запечатать кампанию.

`--skip-specs` допустим только когда утверждённая спека явно описывает чистый рефакторинг, инструментарий или документацию без изменения поведения. Архивация остаётся локальной правкой и не разрешает commit, push, PR или изменения Jira.
