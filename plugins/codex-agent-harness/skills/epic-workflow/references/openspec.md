# Слой OpenSpec

OpenSpec хранит согласуемую спеку, а Agent Harness остаётся единственным журналом исполнения. `tasks.md` описывает план; статусы кампании, проверки и ревью живут только в Agent Harness.

## Когда использовать

Используй OpenSpec для активной крупной идеи, неоднозначного изменения, высокого риска или эпика с несколькими задачами. Для такого изменения утверждённая версионированная спека обязательна до реализации. Не используй OpenSpec для слепого контрольного прогона закрытого эпика и не создавай change для одной уже готовой Jira-задачи.

Сначала проверь `openspec` в `PATH` и наличие `openspec/config.yaml` в целевом репозитории. Если компонента нет, подготовь локальный черновик и остановись до реализации: установка CLI или принятие OpenSpec репозиторием требуют отдельного решения. Не устанавливай OpenSpec, не запускай `openspec init` и не меняй схему репозитория без отдельной просьбы.

Во всех вызовах CLI отключай телеметрию через `env OPENSPEC_TELEMETRY=0 openspec ...`.

## Подготовка спеки

1. Прочитай существующие `openspec/specs/` и код, чтобы не создать параллельный контракт на уже описанное поведение.
2. Проверь `env OPENSPEC_TELEMETRY=0 openspec schema which agent-harness`. Если схема доступна, создай change через `env OPENSPEC_TELEMETRY=0 openspec new change <change-id> --schema agent-harness`. Иначе сохрани выбранную репозиторием схему; не копируй и не подменяй её автоматически.
3. Получай актуальные указания через `env OPENSPEC_TELEMETRY=0 openspec instructions <artifact> --change <change-id>` и заполняй артефакты по порядку. Не сохраняй сырой вывод CLI в состоянии кампании.
4. В `proposal.md` зафиксируй цель, изменения, исключения, влияние и открытые продуктовые вопросы. В `specs/` описывай наблюдаемое поведение, состояния, ошибки и проверяемые сценарии без деталей классов и функций. В `design.md` обязательно закрой безопасность и данные, отказ и восстановление, эксплуатацию, совместимость, UI и исходные материалы; неприменимое отметь с причиной. Каждый пункт `tasks.md` должен давать самостоятельный результат и называть способ проверки.
5. Нерешённый вопрос, меняющий требования, архитектурное решение или декомпозицию, вынеси пользователю до выполнения. Вопрос, который безопасно решить во время реализации, оставь явным в спеке.
6. Не добавляй окончательные рекомендации к тестированию: они формируются после реализации из фактического изменения.

Пользователь должен увидеть полный набор артефактов и один раз подтвердить план до кода. Уже переданный пользователем конкретный план с просьбой выполнить его считается подтверждённым.

Первым пунктом `tasks.md` сделай предварительную проверку всех реально нужных возможностей: версий runtime, package manager, доступа к registry, контейнеров и внешних зависимостей. Проверяй сам доступ, а не наличие VPN: в офисной сети тот же ресурс может быть доступен напрямую. Недоступная возможность переводит пункт в `blocked`; `needs_human` используй только если действительно требуется действие или решение пользователя.

Перед `create_campaign` выполни:

```text
env OPENSPEC_TELEMETRY=0 openspec validate <change-id> --strict --no-interactive
```

Передай в кампанию только:

```json
{"kind":"openspec","change_id":"<change-id>"}
```

Сервер сам вычисляет семантический SHA-256 содержимого change и сверяет его перед переходами задач и запечатыванием результата. Состояние checkbox в `tasks.md` в отпечаток не входит. При незакоммиченной спеке координирующее дерево может содержать только пути внутри `openspec/changes/<change-id>/`; любое другое изменение сохраняет обычную остановку по грязному дереву.

## Выполнение и завершение

Исполнители читают замороженную спеку, но не редактируют общий `tasks.md`. Ведущий отмечает пункт выполненным только после `record_campaign_task(..., status: complete)` соответствующего прогона.

Изменение смысла утверждённой спеки требует нового подтверждения и новой кампании. Исправление опечатки или отметка выполнения не меняет продуктовый контракт.

При создании кампании добавь после всех пунктов спеки служебную `implementation`-задачу `openspec-finalize` с `role: finalizer`. Она зависит от всех задач из `tasks.md`, но собственного checkbox в спеке не имеет.

Для последовательных задач одного репозитория каждая задача после первой использует `base_from_task` и начинается от чистого атомарного коммита предшественника. Для двух и более задач добавь перед `openspec-finalize` отдельную задачу с `role: integration`: она зависит от всех реализаций, смотрит объединённый diff от исходной базы и проходит полный набор проверок и собственное независимое ревью.

После `terminal complete` всех задач из `tasks.md` ведущий отмечает их пункты и запускает для `openspec-finalize` отдельный v1 `workflow`:

1. убедиться, что все пункты `tasks.md` отмечены;
2. снова запустить строгую проверку change;
3. выполнить `env OPENSPEC_TELEMETRY=0 openspec archive <change-id> -y`;
4. включить изменённые основные спеки и архивный каталог в diff этого прогона;
5. выполнить `plan_checks`, проектные проверки и независимое ревью;
6. после `terminal complete` связать прогон со служебной задачей и только затем запечатать кампанию.

`--skip-specs` допустим только когда утверждённая спека явно описывает чистый рефакторинг, инструментарий или документацию без изменения поведения. Архивация остаётся локальной правкой и не разрешает commit, push, PR или изменения Jira.
