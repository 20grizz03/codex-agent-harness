# Пример спецификации задачи: receive-status

Это пример содержания `.agent-harness/specs/delivery-status/tasks/receive-status.md`. Имя файла должно совпасть с идентификатором задачи кампании; разделы можно менять.

Задача принимает HTTP-событие провайдера, проверяет подпись и атомарно применяет статус к существующему сообщению. Невалидная подпись не допускает запись. Повтор события не создаёт второй переход; более старый статус не отменяет `delivered`; неизвестное сообщение не создаётся. Ошибку хранилища можно безопасно повторить. Чтение через API и пользовательский экран сюда не входят.

Проверка через входной HTTP-адаптер: неверная подпись не меняет данные; последовательность `sent → delivered → sent` оставляет `delivered`; двойное `delivered` сохраняет одну запись перехода; ошибка записи и повтор дают тот же результат, что одна успешная обработка. Формат события, подпись и ответы при ошибках определяет закреплённый контракт провайдера из общей спеки.

В учебном примере существующий `TestInvalidSignaturePreservesState` уже проверяет отказ без записи: его сохраняем и запускаем, новый дубль не нужен. Недостающие проверки переходов и ошибки записи добавляем рядом в стиле проекта. Достаточна интеграционная граница входного адаптера и временного хранилища; сквозное чтение через другой API проверяет интеграция эпика. Ожидание — сохранённый статус и число переходов из контракта, а не вычисление тем же алгоритмом, что в обработчике. Данные синтетические, хранилище отдельное на тест, внешние вызовы подменены, очистка выполняется и при ошибке. Команда примера — `make test-receive-status`, затем обязательные проверки проекта; в настоящей задаче указываются обнаруженные имена тестов и команды, а не эти условные значения.

Планируемый PR охватывает входной адаптер, проверку, обработку и сохранение статуса вместе с тестами: одно завершённое поведение. Оценка рабочего кода — около 500 изменённых строк; тесты учитываются отдельно. Задача не зависит от других изменений эпика и может быть проверена и выпущена отдельно; волну и публикационную зависимость ведущий хранит в контракте кампании.
