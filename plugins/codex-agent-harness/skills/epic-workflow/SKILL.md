# Epic Workflow

Codex остаётся ведущим. Используй нативный план Codex для очереди работ и MCP-пространство `agent-harness` для устойчивого состояния кампании; не добавляй собственный планировщик или фоновый процесс.

Выбери один режим:

- для активного эпика, идеи, сложной одиночной задачи или набора задач полностью прочитай [обычный путь эпика](references/live-epic.md);
- для контрольного прогона по закрытому эпику полностью прочитай [слепой контрольный прогон](references/closed-epic-replay.md).

Для активной крупной идеи, неоднозначного или высокорискового изменения, эпика с несколькими задачами либо одной задачи со сложным поведением также полностью прочитай [интеграцию OpenSpec](references/openspec.md): утверждённая спека для них обязательна. Количество Jira-задач не определяет необходимость спеки. По умолчанию держи `/openspec` локально в проекте и исключай весь каталог из Git. Не устанавливай OpenSpec автоматически.

Сначала получи исходные данные через Jira MCP. Для PR, ревью, статусов и проверок в `<repository-host>` предпочитай GitHub Enterprise MCP; код и историю веток читай через локальный `git` по SSH. Если Enterprise MCP недоступен, используй `gh --hostname <repository-host>`, а браузер оставь последним вариантом.

После безопасного чтения и декомпозиции вызови `create_campaign`. Для локального OpenSpec передай только `kind: openspec` и `change_id`: сервер проверит Git ignore, заморозит SHA-256 и сохранит закрытый снимок. `storage: repository` передавай лишь когда команда уже версионирует OpenSpec или пользователь явно выбрал этот режим. Каждую задачу типа `implementation` проводи через отдельный навык `workflow` и связывай с завершённым прогоном v1 через `record_campaign_task`. Не сохраняй сырой ответ Jira/GitHub, полные комментарии, содержимое изменений, токены или аргументы инструментов в состоянии кампании.

При `create_run` передавай ссылку `campaign` с рабочим каталогом кампании, `campaign_id` и `task_id`. Сервер наследует минимальный риск, проверяет базу задачи, сохраняет версию исполнения и применяет общий предохранитель Anthropic. После подтверждённого лимита новые модельные этапы пропускаются до конца интервала: критик получает явно помеченный Codex fallback, а выбранный Claude-исполнитель — терминальный операционный сбой без fallback. После интервала допускается одна проба. Успех пробы закрывает предохранитель, новый лимит продлевает его, а другая ошибка не разрешает fallback.

Обновлять плагин во время долгой кампании можно между волнами задач, когда нет активного модельного этапа. Завершённые и активные прогоны сохраняют свою версию; следующая задача фиксирует более новую версию как безопасную контрольную точку. Проверяемый откат на старую сборку сервер отвергает. Не переустанавливай плагин посреди активного этапа.

Ведущий Codex управляет кампанией, зависимостями и интеграцией, но не реализует задачи сам. Для каждой готовой `implementation`-задачи запускай отдельного нативного вспомогательного агента через `spawn_agent` с `fork_turns: "none"`. Передавай ему только контракт задачи, рабочее дерево, `base_sha`, границы путей, проверки и путь к закрытому снимку спеки `<git_common_dir>/codex-agent-harness/campaigns/<campaign-id>/spec`; не передавай полные отчёты соседних задач. Исполнитель читает снимок без записи, ведёт один `workflow`, возвращает `run_id` и короткий итог, после чего его можно продолжить через `followup_task`.

Одновременно могут писать код не более трёх исполнителей. Независимые задачи разных репозиториев можно запускать сразу. Задачи одного репозитория тоже можно распараллелить от одного зафиксированного `base_sha` в отдельных рабочих деревьях, только если у них нет зависимости и ожидаемые области изменений не пересекаются. При неясных границах выполняй их последовательно. У каждой задачи остаются собственный `run_id`, проверки и отдельное независимое ревью; не объединяй ревью связанного блока.

Оставляй свободное место для проверяющего. При стандартном лимите в четыре активных агента допустимы ведущий и три исполнителя на стадии написания либо ведущий, два исполнителя и один проверяющий на стадии ревью. Если три исполнителя уже заняли места, первый дошедший до ревью сохраняет контрольную точку и завершает ход; ведущий запускает проверяющего, а затем продолжает того же исполнителя. Проверяющих нескольких задач запускай по очереди.

Параллельный блок одного репозитория должен быть последним блоком его реализации в кампании. Заранее добавь отдельную `implementation`-задачу интеграции, зависящую от всех задач блока. Каждый исходный исполнитель создаёт один локальный атомарный коммит до финальных `plan_checks`, независимого ревью и `finish_run`; после корректировки обновляет этот коммит и заново запускает устаревшие проверки. Точные сообщения исходных и интеграционных коммитов включи в согласуемый план кампании, а вместе с `run_id` возвращай итоговый commit SHA.

Исполнитель интеграции вызывает `create_run` в чистом выделенном рабочем дереве до первого слияния. В его неизменяемом контракте заморозь идентификаторы исходных задач и SHA коммитов, затем влей каждый коммит через `git merge --no-ff` с согласованным сообщением. Для каждого SHA добавь обязательную проверку `git merge-base --is-ancestor <sha> HEAD`. Только после этого проводи объединённый результат через полный `workflow` с новыми проектными проверками и отдельным ревью. Это ревью дополняет, а не заменяет ревью исходных задач.

После запуска вспомогательных агентов жди их через `wait_agent` и короткие прямые сообщения. Полученный итог сохрани в плане кампании и не вызывай `list_agents` лишь для повторного чтения уже доставленного полного отчёта; используй список только когда неизвестен текущий состав или состояние агентов.

До первой правки покажи один сводный план кампании: порядок задач, затрагиваемые репозитории, границы и проверки. Для каждого самостоятельного PR или Jira-результата укажи будущую отдельную видимую задачу публикации; подтверждение плана явно разрешает создать её после локальной готовности. Дождись одного подтверждения на весь план; если пользователь уже передал конкретный план с просьбой выполнить его, считай его согласованным, но создание задачи публикации считай разрешённым только тогда, когда она явно была в этом плане. После этого не запрашивай разрешение на код отдельно для каждой задачи. Новый вопрос нужен только при существенном изменении продуктового контракта или области, пересечении с уже изменёнными пользователем файлами либо перед внешним или необратимым действием. Зафиксируй краткую причину и исход через `record_campaign_intervention`.

`complete` означает готовый локальный результат. Исполнители отдельных прогонов возвращают ведущему только `run_id`, SHA и короткий итог. Как только самостоятельно публикуемая Jira-задача получает `complete`, ведущий сразу передаёт её в свежую видимую задачу публикации и продолжает кампанию; завершения соседних задач и всей кампании ждать не нужно. Если несколько реализаций намеренно входят в один PR, передачу создавай после `complete` их интеграционной задачи. `push` и создание PR требуют явного подтверждения, как и любые изменения Jira. Комментарий, разрешение обсуждения, развёртывание, миграция и другие внешние записи тоже не следуют из согласования плана.
