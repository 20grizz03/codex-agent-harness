# Epic Workflow

Codex остаётся ведущим. Используй нативный план Codex для очереди работ и MCP-пространство `agent-harness` для устойчивого состояния кампании; не добавляй собственный планировщик или фоновый процесс.

Выбери режим и полностью прочитай нужный справочник:

- активный эпик, идея или сложная задача — [обычный путь](references/live-epic.md);
- закрытый эпик для контрольного прогона — [слепой прогон](references/closed-epic-replay.md).

Для активной крупной, неоднозначной, высокорисковой или многозадачной работы также прочитай [интеграцию OpenSpec](references/openspec.md). Если пользователь просит выполнить одну сложную задачу, меняющую параллелизм, повторы, частичный отказ, согласованность, безопасность, совместимость или несколько интеграций, OpenSpec также обязателен.

До задач реализации подтверди техническую готовность; при её отсутствии укажи `analysis_required`. Проверь затронутые компоненты и репозитории, контракты с закреплёнными версиями и доступностью, состояния и ошибки, восстановление, совместимость, порядок внедрения, публикацию и откат. Каждое требование должно быть покрыто задачей, а каждая задача — хотя бы одним проверяемым сценарием. Не требуется заранее выбирать внутренние имена и структуры. Вопрос, меняющий продукт, область или границы задач, получает отдельную исследовательскую задачу вида `analysis`; обычное техническое решение принимает ведущий.

Декомпозируй по наблюдаемому поведению. Ориентир — 300–700 изменённых строк рабочего кода; тесты, документацию, конфигурацию, сгенерированные и бинарные файлы учитывай отдельно. Это мягкий бюджет. Связный срез можно оставить крупнее с конкретной причиной, если промежуточный результат нельзя безопасно собрать, проверить, опубликовать или откатить.

После безопасного чтения и согласования вызови `create_campaign`. Задачи хранят `done_when`, ограничения, проверки, закреплённые `contract_refs`, `review_budget`, бюджеты исправлений и повтора критика, `wave`, стратегию зависимостей и `execution`. Рантайм по умолчанию хранит `escalation_model: null`; для подготовленных задач этого сценария план явно выбирает `gpt-6-astra`. Используй:

```yaml
execution:
  native_model: gpt-5.6-sol
  reasoning_effort: high
  escalation_model: gpt-6-astra
max_correction_passes: 2
max_critic_retries: 1
```

Ведущий передаёт настройки контракта в реальные параметры `spawn_agent`: `model: execution.native_model`, `reasoning_effort: execution.reasoning_effort` и `fork_turns: "none"`. MCP только хранит постановку и не подтверждает фактически запущенную модель. Сильную модель ведущего используй для планирования и зафиксированной эскалации. Для каждой задачи вида `implementation` создавай связанный прогон по инструкции `workflow`; сервер наследует постановку, а прогон может только добавить критерии, ограничения, нецели, запрещённые действия и проверки. Совпадающую проверку или зафиксированную настройку переопределять нельзя.

Готовые независимые задачи одной волны запускай в отдельных рабочих деревьях, до трёх исполнителей одновременно. Отдельная задача `kind: implementation`, `role: integration` нужна при объединении нескольких срезов волны; следующая волна начинается от её проверенного коммита. Для единственного среза используй его завершённый проверенный SHA напрямую через `base_from_task`, без искусственного слияния и нового ревью идентичного дерева. Старые контракты кампаний не переписывай. Поля `dependencies` и `wave` управляют локальным порядком реализации. `dependency_strategy: parallel | stacked | after_merge` описывает публикацию и порядок внешнего выпуска; `after_merge` сам по себе не блокирует локальную реализацию готовой задачи.

Каждый исходный исполнитель создаёт атомарный локальный коммит до финальных проверок, возвращает `run_id` и SHA. Интеграционный исполнитель закрепляет SHA исходных задач, объединяет их согласованными коммитами слияния, проверяет происхождение каждого SHA и проводит общий результат через полные проверки и отдельное ревью. Интеграция получает `report_only` и не становится продуктовым PR.

Claude остаётся свежим независимым критиком. Один явный повтор разрешён только после `transient_timeout` или `transient_process_failure` и только по сохранённому бюджету. Подтверждённый лимит Anthropic сохраняет общий период блокировки, одну позднюю пробу и явно помеченный `codex_fallback`; ограничения оплаты, безопасности и чтения не обходятся. Для исправлений используй [повторное ревью и несемантическое завершение](../workflow/references/review-followups.md): новый код требует новых проверок и ревью затронутого поведения, редакционный P3 может завершаться без повторной модели с сохранением происхождения ревью.

Пользователь подтверждает продуктовый план один раз. Разрешение сохраняется между ходами и покрывает обратимые локальные действия, согласованные коммиты и неизменившиеся повторы. Однозначное несемантическое пересечение с пользовательским файлом разрешай безопасно сам. Запрашивай решение только при изменении продукта или области, конфликте с неясным пользовательским намерением либо перед ещё не разрешённым внешним или необратимым действием. Технические решения внутри утверждённого контракта принимает ведущий.

По умолчанию публикационный пакет готовится в текущей пользовательской задаче после проверки всех кандидатов. Отдельную свежую задачу создавай только по явному выбору пользователя. `publication_context`, распознавание конкретного разрешённого действия и проверка каждого кандидата обязательны в обоих случаях. Локальная готовность не разрешает отправку ветки, PR, изменение Jira, слияние, развёртывание или миграцию.

Состояние хранит только очищенные структурированные данные. Не сохраняй сырые ответы Jira/GitHub, модельные потоки, полные комментарии, токены, значения окружения или аргументы инструментов. Не запускай второй MCP-сервер. Обновляй плагин в долгой кампании только между волнами, когда нет задач `in_progress`, активной пробы Anthropic или модельного этапа. Версия каждого прогона фиксируется; сервер отвергает откат на более старую сборку.
