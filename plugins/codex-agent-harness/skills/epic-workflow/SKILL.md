# Epic Workflow v2.1

Codex остаётся ведущим. Используй нативный план Codex для очереди работ и MCP-пространство `agent-harness` для устойчивого состояния кампании; не добавляй собственный планировщик или фоновый процесс.

Выбери один режим:

- для активного эпика, идеи или набора задач полностью прочитай [обычный путь эпика](references/live-epic.md);
- для контрольного прогона по закрытому эпику полностью прочитай [слепой контрольный прогон](references/closed-epic-replay.md).

Сначала получи исходные данные через Jira MCP. Для PR, ревью, статусов и проверок в `<repository-host>` предпочитай GitHub Enterprise MCP; код и историю веток читай через локальный `git` по SSH. Если Enterprise MCP недоступен, используй `gh --hostname <repository-host>`, а браузер оставь последним вариантом.

После безопасного чтения и декомпозиции вызови `create_campaign`. Каждую задачу типа `implementation` проводи через отдельный навык `workflow` и связывай с завершённым прогоном v1 через `record_campaign_task`. Не сохраняй сырой ответ Jira/GitHub, полные комментарии, содержимое изменений, токены или аргументы инструментов в состоянии кампании.

Ведущий Codex управляет кампанией, зависимостями и интеграцией, но не реализует задачи сам. Для каждой готовой `implementation`-задачи запускай отдельного нативного вспомогательного агента через `spawn_agent` с `fork_turns: "none"`. Передавай ему только контракт задачи, рабочее дерево, `base_sha`, границы путей и проверки; не передавай полные отчёты соседних задач. Исполнитель ведёт один `workflow`, возвращает `run_id` и короткий итог, после чего его можно продолжить через `followup_task`.

Одновременно могут писать код не более трёх исполнителей. Независимые задачи разных репозиториев можно запускать сразу. Задачи одного репозитория тоже можно распараллелить от одного зафиксированного `base_sha` в отдельных рабочих деревьях, только если у них нет зависимости и ожидаемые области изменений не пересекаются. При неясных границах выполняй их последовательно. У каждой задачи остаются собственный `run_id`, проверки и отдельное независимое ревью; не объединяй ревью связанного блока.

Оставляй свободное место для проверяющего. При стандартном лимите в четыре активных агента допустимы ведущий и три исполнителя на стадии написания либо ведущий, два исполнителя и один проверяющий на стадии ревью. Если три исполнителя уже заняли места, первый дошедший до ревью сохраняет контрольную точку и завершает ход; ведущий запускает проверяющего, а затем продолжает того же исполнителя. Проверяющих нескольких задач запускай по очереди.

Параллельный блок одного репозитория должен быть последним блоком его реализации в кампании. Заранее добавь отдельную `implementation`-задачу интеграции, зависящую от всех задач блока. Каждый исходный исполнитель создаёт один локальный атомарный коммит до финальных `plan_checks`, независимого ревью и `finish_run`; после корректировки обновляет этот коммит и заново запускает устаревшие проверки. Точные сообщения исходных и интеграционных коммитов включи в согласуемый план кампании, а вместе с `run_id` возвращай итоговый commit SHA.

Исполнитель интеграции вызывает `create_run` в чистом выделенном рабочем дереве до первого слияния. В его неизменяемом контракте заморозь идентификаторы исходных задач и SHA коммитов, затем влей каждый коммит через `git merge --no-ff` с согласованным сообщением. Для каждого SHA добавь обязательную проверку `git merge-base --is-ancestor <sha> HEAD`. Только после этого проводи объединённый результат через полный `workflow` с новыми проектными проверками и отдельным ревью. Это ревью дополняет, а не заменяет ревью исходных задач.

После запуска вспомогательных агентов жди их через `wait_agent` и короткие прямые сообщения. Полученный итог сохрани в плане кампании и не вызывай `list_agents` лишь для повторного чтения уже доставленного полного отчёта; используй список только когда неизвестен текущий состав или состояние агентов.

До первой правки покажи один сводный план кампании: порядок задач, затрагиваемые репозитории, границы и проверки. Дождись одного подтверждения на весь план; если пользователь уже передал конкретный план с просьбой выполнить его, считай его согласованным. После этого не запрашивай разрешение на код отдельно для каждой задачи. Новый вопрос нужен только при существенном изменении продуктового контракта или области, пересечении с уже изменёнными пользователем файлами либо перед внешним или необратимым действием. Зафиксируй краткую причину и исход через `record_campaign_intervention`.

`complete` означает готовый локальный результат. `push` и создание PR требуют явного подтверждения, как и любые изменения Jira. Комментарий, разрешение обсуждения, развёртывание, миграция и другие внешние записи тоже не следуют из согласования плана.
