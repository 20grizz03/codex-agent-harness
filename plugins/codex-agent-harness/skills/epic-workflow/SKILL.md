# Epic Workflow v2.1

Codex остаётся ведущим. Используй нативный план Codex для очереди работ и MCP-пространство `agent-harness` для устойчивого состояния кампании; не добавляй собственный планировщик или фоновый процесс.

Выбери один режим:

- для активного эпика, идеи или набора задач полностью прочитай [обычный путь эпика](references/live-epic.md);
- для контрольного прогона по закрытому эпику полностью прочитай [слепой контрольный прогон](references/closed-epic-replay.md).

Сначала получи исходные данные через Jira MCP. Для PR, ревью, статусов и проверок в `<repository-host>` предпочитай GitHub Enterprise MCP; код и историю веток читай через локальный `git` по SSH. Если Enterprise MCP недоступен, используй `gh --hostname <repository-host>`, а браузер оставь последним вариантом.

После безопасного чтения и декомпозиции вызови `create_campaign`. Каждую задачу типа `implementation` проводи через отдельный навык `workflow` и связывай с завершённым прогоном v1 через `record_campaign_task`. Не сохраняй сырой ответ Jira/GitHub, полные комментарии, содержимое изменений, токены или аргументы инструментов в состоянии кампании.

До первой правки покажи один сводный план кампании: порядок задач, затрагиваемые репозитории, границы и проверки. Дождись одного подтверждения на весь план; если пользователь уже передал конкретный план с просьбой выполнить его, считай его согласованным. После этого не запрашивай разрешение на код отдельно для каждой задачи. Новый вопрос нужен только при существенном изменении продуктового контракта или области, пересечении с уже изменёнными пользователем файлами либо перед внешним или необратимым действием. Зафиксируй краткую причину и исход через `record_campaign_intervention`.

`complete` означает готовый локальный результат. `push` и создание PR требуют явного подтверждения, как и любые изменения Jira. Комментарий, разрешение обсуждения, развёртывание, миграция и другие внешние записи тоже не следуют из согласования плана.
