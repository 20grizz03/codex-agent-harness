# Delivery Writing

Пиши по фактическому состоянию задачи, кода и PR. Не дополняй текст предполагаемым поведением и не превращай частный пример в обязательное правило для другого проекта.

Для любого русского текста сначала прочитай [правила русского технического текста](references/russian-writing.md). Затем открой только нужный справочник:

- для постановки Jira-задачи — [формат задачи](references/jira-task.md);
- для блока, который добавляется после реализации, — [рекомендации к тестированию](references/testing-recommendations.md);
- для описания PR — [краткое описание PR](references/pr-description.md);
- для текста комментариев коллегам — [комментарии к ревью](references/review-comments.md);
- перед пакетом публикации — [локальная ручная проверка](references/manual-smoke.md).

Перед публикационным пакетом полностью прочитай [контекст публикации](references/publication-context.md). Явный `publication_context.active: true` означает, что текущая пользовательская задача уже владеет пакетом и не должна передавать его дальше. Для старых задач применяй описанные там признаки обратной совместимости.

Рекомендации к тестированию составляй после реализации, когда доступны фактическое изменение, контракт и результаты проверок. Описывай только поведение текущего PR, даже если он входит в большой эпик. До этого фиксируй только критерии готовности и открытые продуктовые вопросы.

По умолчанию готовь черновик в чате. Подготовка текста не разрешает создание или изменение PR, изменение Jira, публикацию комментария или разрешение обсуждения. Перед любым изменением Jira покажи полный предлагаемый блок `## Рекомендации к тестированию` и дождись явного подтверждения.

В текущей задаче сначала проверь все `source_run_ids` и, если есть, `campaign_id` через Agent Harness, затем сверь пакет по текущему Git, Jira и PR и самостоятельно прочитай полный результат каждого кандидата от его базового SHA. Расхождение статуса, отпечатка, путей, проверок, актуального ревью или Git останавливает весь пакет. После сверки выполни локальную ручную проверку. Подготовь одним сообщением описание сделанного, размеры рабочего кода, тестов, документации и конфигурации, сгенерированных и бинарных файлов, статус мягкого бюджета, раздел `## Локальная ручная проверка`, commit, заголовок и короткое описание PR, полный блок `## Рекомендации к тестированию` и список предлагаемых внешних действий.

После показа всего пакета однозначная команда пользователя разрешает названные в ней действия из показанного списка. Формулировка не обязана совпадать с `публикуем`: например, `пушим поверх` разрешает показанные commit и обычный push без `--force`, а `создавай PR` — только показанное создание или обновление PR. Если команда называет часть пакета, выполняй только её. Вне показанного пакета такая фраза не расширяет разрешения.

Перед первой записью ещё раз обнови состояние ветки, PR, проверок и Jira. Если оно отличается от показанного пакета, ничего не меняй: покажи обновлённый пакет и дождись нового подтверждения. После временного сбоя повторяй уже разрешённое действие без новой команды, пока кандидат, целевая ветка и список действий не изменились. Новый пакет и подтверждение нужны при изменении diff или commit, другой ветке, force-push либо добавлении внешнего действия. Разрешение не включает merge, изменение статуса задачи, развёртывание, миграцию, непоказанные комментарии или другие внешние действия. Для комментариев к ревью по-прежнему показывай точные формулировки и жди отдельной команды.

С момента установки `publication_context` эта задача остаётся рабочим контекстом пакета: подготовь публикацию, проверь CI, обработай замечания ревью и разбери состояние или сбой развёртывания здесь. Отдельную свежую задачу создавай только по явному выбору пользователя. Если требуется кодовый фикс, проведи его через `workflow` и верни результат сюда; развёртывание и миграция сохраняют отдельные границы разрешения.
