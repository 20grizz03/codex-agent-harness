# Контекст публикации

Перед подготовкой пакета установи в текущей пользовательской задаче явный служебный блок. Если пользователь отдельно выбрал свежую задачу для изоляции, передай туда тот же блок:

```yaml
publication_context:
  active: true
  scope_id: <стабильный идентификатор пакета>
  source_run_ids:
    - <run-id>
  source_issue: <Jira-задача или локальная ссылка>
  candidates:
    - run_id: <run-id>
      workspace: <рабочий каталог прогона>
      repository: <репозиторий>
      candidate_worktree: <неизменяемое рабочее дерево>
      base_sha: <базовый SHA>
      final_sha: <итоговый SHA>
      committed: <true или false>
      source_branch: <ветка или отсутствует>
      remote: <remote>
      pull_request_target: <целевая ветка PR>
      diff_fingerprint: <отпечаток diff>
      changed_paths: [<пути>]
      review: <вердикт и источник>
```

`scope_id` обозначает один согласованный пакет доставки: один PR, несколько намеренно связанных PR либо один Jira-результат, который пользователь явно попросил публиковать вместе. Для одиночного прогона используй `run:<run-id>`, для общей интеграционной поставки — стабильный идентификатор кампании и интеграционной задачи. Не меняй `scope_id`, когда к уже согласованному пакету добавляется ещё один проверенный кандидат; добавь его `run_id` в `source_run_ids` и отдельный связанный блок в `candidates`. Не передавай сведения разных кандидатов параллельными списками.

Блок является указанием роли текущей задачи, а не разрешением на внешние действия. При `active: true` эта задача уже владеет подготовкой и сопровождением публикации своего `scope_id` и не должна вызывать `create_thread` для:

- первоначальной подготовки пакета;
- дополнительного backend, frontend или другого кандидата того же пакета;
- обновления описания PR и рекомендаций к тестированию;
- CI, замечаний ревью и диагностики развёртывания;
- кодового исправления по режиму мелкой доработки либо через отдельный `workflow` в этом же контексте.

Если пользователь явно добавляет в текущую задачу ещё один кандидат того же Jira-результата или просит опубликовать кандидаты вместе, проверь его `run_id`, Git и внешнее состояние на общих основаниях, расширь текущий пакет и заново покажи полный набор действий. Не передавай кандидаты в следующую задачу. Изменившийся пакет требует нового подтверждения перед внешней записью.

Не объединяй молча независимые Jira-задачи или PR. Другой самостоятельно публикуемый результат получает отдельный `scope_id`; новую пользовательскую задачу для него создавай только по явному выбору пользователя.

Для старой задачи без служебного блока создай блок перед подготовкой публикации из проверенных данных прогона. Прежний формат отдельной задачи не содержит историю его реализации; это признак обратной совместимости, а не нынешнее требование. Если старая передача содержит одиночный `run_id`, нормализуй его в `source_run_ids`, выведи `scope_id` как `run:<run-id>` и собери один кандидатский блок. История реализации не мешает публикации в текущей задаче, но не заменяет повторную проверку всех кандидатов.

## Мелкие доработки

Выбирай этот режим до `create_run`, когда текущая задача уже сопровождает проверенный кандидат и пользователь попросил узкое исправление внутри согласованного результата: например, уточнить текст ошибки или исправить очевидную локальную ошибку по замечанию ревью. Допустима правка кода; количество строк само по себе не определяет риск. Первичная реализация и незавершённый прогон с замечаниями или непройденными проверками сюда не относятся.

Кратко обозначь исправление и границы, внеси его и самостоятельно прочитай diff. Не создавай новую задачу, кампанию, OpenSpec или прогон. Не запускай автоматически тесты, линтеры, ручной сценарий, Claude или резервного проверяющего. Проверку запускай только по конкретной необходимости, объяснив причину, либо по просьбе пользователя; предварительная проверка безопасности исходящего трафика сохраняется. Этот режим снимает требования Agent Harness, но не отдельное явное требование пользователя или обязательную проверку из правил репозитория; о таком требовании сообщи до запуска.

Если исправление меняет требования, безопасность, работу с данными, совместимость, порядок остановки или восстановления, затрагивает несколько зависимых PR либо требует архитектурного решения, останови расширение, объясни риск и согласуй обновлённый план обычного `workflow`/`epic-workflow`. Не разбивай большую доработку на мелкие, чтобы остаться в этом режиме: оценивай весь накопленный diff относительно проверенной основы.

Сохрани исходный блок кандидата и его завершённый `run_id` как проверенную основу. До первой правки сверь его с Git и не меняй исходное рабочее дерево: используй отдельное рабочее дерево от проверенного коммита. Для незакоммиченного кандидата сначала обеспечь отдельную воспроизводимую копию полного результата, включая индекс и новые файлы, без потери пользовательских изменений и без неразрешённого коммита. Если основу нельзя достоверно восстановить, этот режим неприменим.

В блок кандидата добавь `follow_up` с полями:

- `mode: small_publication_fix`, причина выбора и краткий перечень исправлений;
- `baseline_fingerprint` исходного прогона;
- рабочее дерево текущей версии, её `HEAD`, состояние индекса, изменённые и новые пути и отпечаток полного результата, включая содержимое новых файлов;
- `checks: not_run`, `independent_review: not_run`, `manual_smoke: not_run` либо фактически выполненные проверки с их результатами и версией кода;
- ограничения проверки и остаточные риски.

Это данные пакета в текущей задаче, а не новый формат состояния MCP. `source_run_ids` и исходный `run_id` остаются ссылками только на проверенную основу. Не переписывай `contract.json`, `state.json` или `review.json`, не вызывай `finish_run(complete)` для непроверенной версии и не помечай старые проверки или ревью актуальными. Режим нельзя использовать как проверенную интеграционную основу следующей волны или как результат контрольного прогона закрытого эпика.

При подготовке и непосредственно перед публикацией проверь неизменность основы, текущей версии и весь diff между ними. Только явно перечисленные доработки объясняют расхождение с исходным отпечатком; неизвестные изменения, чужие правки или изменившаяся целевая ветка останавливают публикацию. Для остальных кандидатов пакета сохраняется обычная сверка. Если доработки больше нет и результат точно совпадает с проверенной основой, удали `follow_up` и используй обычные подтверждения основы.

В обновлённом пакете явно напиши: «Доработка: <что изменено>. Тесты и независимое ревью после неё не запускались; прежние результаты относятся к исходной версии». Для ручной проверки укажи `не запускалась — режим мелкой доработки`. Не выдавай такой результат за полностью проверенный. Покажи актуальные commit/PR/Jira-тексты и внешние действия; изменение кандидата требует нового подтверждения публикации. Разрешение исправить код не разрешает commit, push, изменение PR или Jira, merge, развёртывание либо миграцию. CI и обязательные правила удалённого репозитория не обходятся.
