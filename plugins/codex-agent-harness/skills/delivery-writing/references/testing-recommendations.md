# Рекомендации к тестированию

Готовь этот блок после реализации и создания либо подготовки PR. Источники истины — текущая Jira-задача, фактический diff, контракт API или UI и результаты проверок. Если они расходятся, сначала зафиксируй расхождение; не маскируй его рекомендациями.

## Содержание

Начни с минимальных тестовых данных и нужного бизнес-состояния. Затем дай точное действие через `curl`, CLI или UI с безопасными заполнителями. Укажи наблюдаемый результат:

- HTTP-статус, ключевые поля ответа и обязательные заголовки;
- переходы состояния и ожидаемые побочные эффекты;
- поля и данные, которых в ответе, логах или хранилище быть не должно;
- безопасный способ получить тестовое значение, если продуктовый сценарий его не показывает;
- короткий раздел `Дополнительно проверить` с ошибочными ветками, идемпотентностью и конкретным регрессом.

Если остаётся согласованный неочевидный компромисс, закончи им блок, чтобы QA не оформил ожидаемое поведение как дефект. Не пересказывай всю задачу и не пиши «провести полный регресс».

Перед локальными командами и интеграционными сценариями проверь направления исходящего трафика. Реальные SMTP, SMS, WhatsApp, push, очереди и общие окружения разрешены только в контролируемом сценарии с согласованным тестовым получателем.

## Каркас

````text
## Рекомендации к тестированию

Подготовить <минимальные данные и состояние>.

```bash
<точная команда с заполнителями>
```

Ожидается <статус, поля, переход состояния и отсутствие чувствительных данных>.

### Дополнительно проверить

- <граничный или ошибочный сценарий>;
- <идемпотентность или повторный вызов>;
- <конкретный регресс существующего поведения>.

<Согласованный компромисс, если он есть>.
````

Перед публикацией адаптируй Markdown к формату текущего поля Jira только при необходимости; смысл и полнота блока не должны меняться.

Покажи пользователю весь готовый блок, а не его пересказ. Меняй Jira только после явного подтверждения этой версии.
