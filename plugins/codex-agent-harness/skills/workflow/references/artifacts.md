# Артефакты и контекст кампании

Применяй эти правила при запуске исполнителя, передаче результата и подготовке публикации. Они не меняют закрытые контракты действующих кампаний и не требуют чистки старых файлов.

## Источник истины

- Требования: утверждённый закрытый снимок общей спеки и спеки задачи из `spec_context` либо закреплённый OpenSpec-контракт действующей кампании. Рабочий черновик и старый анализ не расширяют его.
- Исполнение: структурированное состояние кампании, прогона и цепочки корректировок в Agent Harness. Сохраняй там предусмотренные краткие подтверждения; не дублируй их отдельными JSON-выгрузками после каждого шага.
- Код: Git SHA, полный diff от закреплённой базы и рабочее дерево, пока оно нужно исполнителю или проверке. Отдельные деревья для параллельных задач и безопасных исправлений сохраняют свою роль.
- Публикация: один `publication_context` на `scope_id` в текущей пользовательской задаче и один актуальный пакет с кандидатами. Jira и PR становятся источником внешнего состояния после разрешённой записи.

Новый файл анализа создавай, только когда он содержит необходимое решение или воспроизводимые данные, которые не помещаются в спеку, код либо краткое состояние прогона. Укажи его назначение, источник и актуальность; при замене отметь прежний документ как исторический и дай ссылку на действующий. Обновляй текущий черновик вместо новых файлов `attempt-2`, `final-v2` и повторных снимков ответов инструментов. Не удаляй историю, Git worktree или закрытые снимки автоматически. Перед предложением архивации проверь dirty-файлы, непереданные коммиты, активные задачи и доступность закреплённых SHA.

## Передача ровно нужного контекста

Исполнителю передай пути закрытой общей спеки и только его задачи, контракт задачи, базовый SHA, обязательные проверки и точные ссылки на нужные внешние контракты. Спеку зависимости добавляй лишь по указанной в контракте ссылке. Дополнительный анализ, чужие задачи и историю ревью открывай по конкретному вопросу; не прикладывай каталог `publications/`, все рабочие деревья или весь диалог. Критику дай проверяемый Git результат и границы ревью, без вставки сырых логов и полного diff в передаваемый текст. Ведущий получает `run_id`, SHA, статус проверок и краткое ограничение, затем сам запрашивает детали через Agent Harness и Git.

При публикации загружай `get_run` только для `source_run_ids` своего `scope_id`, `get_campaign` при наличии кампании и текущее Git/PR/Jira-состояние только названных кандидатов. Не перечитывай полный набор старых аналитических и публикационных файлов для каждого шага.

## Повтор публикации

Повтор подготовки того же `scope_id` обновляет существующий пакет; не создавай новую задачу, второй `publication_context` или копию репозитория только ради текста. Добавляй кандидата лишь при новом проверенном `run_id` или явно согласованном дополнении пакета. Перед внешним действием сверяй кандидат, целевую ветку, точный текст и набор разрешённых действий. После временного сбоя сначала проверь, не выполнено ли действие уже: существующий PR, комментарий или запись Jira не создавай повторно. Если кандидат, цель или текст изменились, покажи обновлённый пакет и получи разрешение на изменившееся действие по правилам публикации.
