# Native Codex usage observations

The Agent Harness MCP runtime cannot read Codex usage counters on its own. `record_codex_telemetry` is a supported ingestion path for **structured cumulative counters actually exposed to the caller**. Do not infer counters from message length, the account usage window, a model name, or elapsed time. If the task runtime does not expose them, record `availability: unavailable`, `reason: not_exposed`. This is different from a measured zero.

Record one observation for each role and attempt: `lead`, `executor`, or `reviewer`, with `path: primary`, `retry`, or `fallback`. Give the observation a stable `observation_id` so a repeated call is idempotent. `scope_id` identifies the native cumulative stream from which both snapshots came. Provide `baseline` just before the attempt and `final` just after it, with the same counter names. The server calculates nonnegative deltas and rejects overlapping intervals in one scope. If execution stops before a final snapshot, mark `partial` with `reason: interrupted` and provide whichever snapshot exists. Never mark an incomplete pair `available`.

Accepted counters are `input_tokens`, `cached_input_tokens`, `output_tokens`, and `reasoning_output_tokens`, as nonnegative integers. `input_tokens` and `output_tokens` are required for `available`; optional counter names must match between baseline and final. The returned `observed_token_deltas` are sums of submitted, nonoverlapping deltas, split by role; partial observations can contribute only counters for which both snapshots exist. These are observed values, not a guarantee of complete task usage. A campaign and its runs have separate ledgers. Report at the campaign level only a measured interval that is not already being presented as an additive run total. No price or cost is calculated; `cost` remains `null`.

Only allowlisted identifiers and counters are persisted in Git-private state. Do not send raw Codex events, prompts, transcripts, tool arguments, environment values, credentials, or provider logs. The tool accepts observations after a run or campaign reaches a terminal state so a final snapshot can be recorded without reopening the execution contract.
