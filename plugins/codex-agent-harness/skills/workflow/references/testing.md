# Тестирование в рамках задачи

Используй этот справочник внутри текущего этапа планирования, реализации, проверки или подготовки рекомендаций QA. Он не создаёт отдельного прогона, проверяющего или согласования. Уже прочитанные правила не загружай повторно, пока они доступны в контексте.

Сначала выбери маршрут по `workflow`. Для мелкой публикационной доработки сохраняется исключение из обязательных тестов, ручного прогона и независимого ревью: новый код помечается непроверенным. Этот справочник не отменяет исключение и не закрывает незавершённый стандартный прогон. Полный аудит покрытия, подключение Allure/TestOps и смена инструментария требуют отдельной задачи.

## При планировании

Исследуй только поведение задачи и затронутые связи. Найди правила тестирования в `AGENTS.md`, `CLAUDE.md`, доступных проектных навыках, командах и CI; прочитай ближайшие поддерживаемые тесты. Не запускай приложение ради поиска маршрутов, пока не проверена безопасность окружения. Существующие тесты оценивай по подготовке и утверждениям, а не по имени, числу или соседству с кодом.

Для существенного сценария определи ожидаемый результат из согласованного требования, публичного контракта или инварианта, риск ошибки, существующую проверку и нужное дополнение. Выбери самый узкий уровень, который действительно обнаружит эту ошибку:

- отдельное бизнес-правило можно проверить модульным тестом;
- сохранение данных, регистрацию обработчика или взаимодействие компонентов — на соответствующей интеграционной границе;
- согласованность производителя и потребителя — проверкой их контракта;
- сквозной путь нужен, если более узкие проверки не подтверждают значимый конечный результат.

Один сценарий не нужно повторять на всех уровнях. HTTP — лишь один из входов: для очереди, CLI, файла или фоновой задачи проверяй их собственный вход, изменение состояния и существенные побочные эффекты. Не подменяй сохранённый результат только статусом ответа или вызовом мока. Ошибки, права, повторы, конкуренцию и восстановление добавляй по применимому риску, без фиксированного количества тестов на операцию.

В общей спеке эпика оставь существенные межкомпонентные сценарии и общие условия безопасного запуска. В спеке задачи или кратком плане самостоятельной задачи укажи своё поведение, ожидаемый результат, достаточное существующее покрытие либо недостающие тесты, данные и способ запуска. Это часть уже согласуемого плана, а не новый реестр, обязательная таблица, раздел схемы или черновик рекомендаций QA. Если нужной безопасной среды пока нет, обозначь ограничение и способ его снять; обычные технические решения принимай внутри согласованных границ.

## При реализации

После законченного среза добавь или обнови относящиеся к нему тесты, до итогового ревью. Существующего теста достаточно, если его утверждения обнаружат нарушение нужного поведения; назови этот тест и не добавляй дубль. Для исправления дефекта используй воспроизведение как основу регрессионного теста, когда это безопасно и применимо. Не удаляй соседнее покрытие и не реорганизуй всю тестовую систему в рамках этой задачи.

Следуй принятому в репозитории стилю, переиспользуй подходящие фикстуры и средства запуска. Ожидание не вычисляй тем же алгоритмом, который проверяется. Изменение эталона или ослабление утверждения допустимо только вслед за подтверждённым изменением контракта, а не ради зелёного результата. Поддельная зависимость не должна обходить механизм, который тест обещает проверить.

Используй синтетические данные, контролируемые время и случайность, изолированные ресурсы и очистку после частичной подготовки, сбоя и отмены. Повторный запуск не должен зависеть от чужих данных или порядка тестов. Перед выполнением сохраняй правила проверки исходящего трафика из основного протокола; уникальный идентификатор записи сам по себе не делает общее окружение безопасным.

### Подсказки для уже принятого инструментария

- **Go с Allure:** сначала найди реальную структуру suite/steps и настройки запуска проекта. HTTP-обёртки не должны содержать проверяемую бизнес-логику. Зарегистрируй очистку сразу после получения ресурса; критичная ошибка подготовки должна останавливать зависимые шаги. Сохраняй читаемые названия и диагностику первого сбоя, не добавляй повтор всей suite по умолчанию. Не переноси Allure в обычные Go-тесты только из-за этой подсказки.
- **Codeception:** используй существующие Cest, вспомогательные классы, фикстуры и принятый способ оформления шагов. Подменяй зависимости с внешними эффектами до их использования. Запускай конкретный тест поддерживаемой командой проекта; не добавляй глобальный Pint, автоисправления каталогов или второй конкурирующий форматтер. Наличие Codeception не означает наличие AllureHelper.

Не копируй версии библиотек, имена контейнеров, адреса и команды из другого сервиса. Для Go зависимости файлов с пользовательскими build tags учитываются обычным `go mod tidy`; исключение — `ignore`. Изменение зависимостей само по себе требует проверки diff `go.mod`/`go.sum`, но не установки нового фреймворка. См. [официальное описание `go mod tidy`](https://go.dev/ref/mod#go-mod-tidy).

## При выполнении проверок

Во время написания запускай относящийся к изменению тест для быстрой обратной связи. Для итогового текущего diff сначала выполни `git diff --check`, затем затронутые тесты и все обязательные проверки из `plan_checks`. Узкий прогон не заменяет обязательную suite. Если команда уже выполнена для того же отпечатка и покрывает ту же проверку, используй её результат без повторного запуска; при новом отпечатке старое подтверждение недействительно.

Проверь, что команда действительно выбрала и выполнила нужные тесты. Код выхода `0` при нуле тестов, полном пропуске или одном только сборочном шаге не доказывает сценарий. Исправь выбор и выполни проверку; если это невозможно, не записывай пустой прогон как успешный `record_check`. Не подменяй фактический код выхода вымышленным. Обязательная проверка остаётся незакрытой, причина явно сообщается. При частичных пропусках перечисли непроверенное поведение и оцени его относительно критериев задачи.

Различай дефект продукта, ошибку теста и недоступность среды. Перед повтором сохрани очищенное краткое описание первого сбоя и причину повтора. Случайный последующий успех не доказывает устранение нестабильности. Повтор допустим для конкретной проверки причины или после исправления; не повторяй до зелёного и не увеличивай тайм-аут без объяснения. В итоговом результате оставь историю сбоя, выполненное исправление или диагностику и оставшееся ограничение.

Для `record_check` передавай фактический код выхода, длительность и краткий очищенный `summary`: выполненные сценарии, существенные пропуски и ограничения, первый сбой и результат обоснованного повтора, если он был. Не сохраняй сырые журналы, тела запросов, секреты или персональные данные. План и фактический результат различаются: написанный тест без запуска остаётся непроверенным, локальная подмена не подтверждает реальную интеграцию. Новых полей MCP для этого не требуется.

## При существующем ревью и передаче QA

Критик сопоставляет утверждения затронутых тестов с контрактом в рамках текущего ревью, без собственного запуска команд и отдельного аудита покрытия. Конкретный дефект теста требует подтверждения, какой значимый сбой останется незамеченным. Недоступная проверка относится к ограничениям подтверждения, а не становится выдуманным дефектом. Процент покрытия и количество тестов не определяют вердикт.

После реализации используй [формат рекомендаций QA](../../delivery-writing/references/testing-recommendations.md). Внутренний подраздел «Автоматически проверено» включает только успешно выполненные для текущего результата API-сценарии из тестов, созданных или изменённых в текущей задаче. Модульные тесты и неизменённые API-тесты в него не попадают; все выполненные проверки сохраняются в техническом отчёте, а обязательный состав проверок не сокращается. Отдели непройденные границы и оставшуюся ручную проверку с учётом всего фактического покрытия, а не только этого подраздела. Назови неочевидные сценарии, затронутые компоненты и безопасный способ воспроизведения; не дублируй весь список тестов и не требуй общего регресса. Сохрани подготовку данных, точное действие, ожидаемый результат и дополнительные проверки нашего формата. Jira меняется только после подтверждения полного текста. Локальная ручная проверка сохраняет собственные правила и не превращается в ещё один полный тестовый цикл.
